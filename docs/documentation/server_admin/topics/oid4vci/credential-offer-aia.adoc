=== Credential Offer via Application Initiated Action

{project_name} provides a built-in <<con-aia_{context},Application Initiated Action (AIA)>> called `verifiable_credential_offer` that allows client applications to trigger credential issuance for a user during login. When this action is triggered, the user is presented with a page containing a QR code that can be scanned by a wallet application to claim the credential.

Both the {project_name} <<_account-service,Account Console>> (*Verifiable credentials* tab → *Issue to wallet*) and the Admin Console (*Users* → *Verifiable Credentials* → *Send credential offer*) use this same AIA under the covers.

This section covers how to configure the action, how to trigger it from your application, and what the user experiences during the flow.

==== Enabling and configuring the action

The `verifiable_credential_offer` action is automatically registered when the `OID4VC_VCI` feature is enabled. You can manage it in the Admin Console:

. Navigate to *Authentication* > *Required actions*.
. Locate the *Register Verifiable Credential Offer* action in the list.

.Required Actions configuration showing the Verifiable Credential Offer action
image::images/oid4vci/screenshot-required-actions-vc-offer.png[Required Actions tab showing the Register Verifiable Credential Offer action with its enabled toggle and re-auth max age setting, width=750]

From here you can:

* **Disable the action** — Toggle it off to prevent any application from triggering credential offers via AIA.
* **Configure re-authentication** — Set the *Max Age* to control how long ago the user must have actively authenticated before being required to re-authenticate when the action is triggered. If not configured, the default is five minutes. See <<con-aia-reauth_{context},Re-authentication during AIA>> for details.

==== Triggering the action from your application

To trigger the credential offer AIA, your application redirects the user to the {project_name} authorization endpoint with the `kc_action` parameter. The parameter value consists of the action name followed by a colon and a Base64Url-encoded JSON configuration:

[source]
----
kc_action=verifiable_credential_offer:<base64url-encoded-config>
----

The JSON configuration object has the following properties:

[cols="1,1,2", options="header"]
|===
| Property
| Required
| Description

| `credentialConfigurationId`
| Yes
| The type of credential to offer. This value must match the *Credential Configuration ID* attribute of an existing OID4VCI client scope (see <<_oid4vci_client_scope,Create Client Scopes with Mappers>>), and the authenticated user must already have this credential assigned (see <<_oid4vci_user_setup,Creating a User Account>>). If the user does not have the credential, the AIA returns `kc_action_status=error`. It identifies a credential _type_ (such as "membership-credential" or "employee-badge"), not a specific issued credential. This is the same identifier that appears in the issuer metadata under `credential_configurations_supported`.

| `preAuthorized`
| No
| If `true`, the credential offer uses the pre-authorized code grant, which requires the `oid4vc-vci-preauth-code` feature to be enabled (`--features=oid4vc-vci-preauth-code`). If `false` or omitted, the authorization code grant is used.

| `clientId`
| No
| The client ID of the OID4VCI-enabled client to which this offer is restricted. This is the human-readable client ID (for example, `my-wallet-client`), not Keycloak's internal UUID. The specified client must be enabled and have OID4VCI turned on. If omitted, the credential offer can be used by any client or wallet.
|===

===== Example

To trigger a credential offer for a credential configuration called `membership-credential` using the authorization code grant:

. Construct the JSON configuration:
+
[source,json]
----
{"credentialConfigurationId":"membership-credential"}
----

. Base64Url-encode the JSON string. For example, the above encodes to:
+
[source]
----
eyJjcmVkZW50aWFsQ29uZmlndXJhdGlvbklkIjoibWVtYmVyc2hpcC1jcmVkZW50aWFsIn0
----

. Append it to the `kc_action` parameter and redirect the user to the authorization endpoint:
+
[source,http]
----
GET /realms/{realm}/protocol/openid-connect/auth
  ?response_type=code
  &client_id=my-app
  &redirect_uri=https://my-app.example.com/callback
  &scope=openid
  &kc_action=verifiable_credential_offer:eyJjcmVkZW50aWFsQ29uZmlndXJhdGlvbklkIjoibWVtYmVyc2hpcC1jcmVkZW50aWFsIn0
----

===== Handling the response

After the user completes or cancels the action, they are redirected back to your application's redirect URI. The redirect includes:

* `kc_action_status=executed` — The user completed the credential offer flow.
* `kc_action_status=cancelled` — The user cancelled the action.

[source]
----
https://my-app.example.com/callback?code=...&kc_action_status=executed&kc_action=verifiable_credential_offer
----

[WARNING]
====
Even if `kc_action_status=executed` is returned, this only means the user completed the AIA flow — it does not guarantee the wallet successfully obtained the credential. The credential is issued asynchronously when the wallet contacts {project_name}'s credential endpoint.
====

==== The credential offer QR code page

When the AIA is triggered and the user has authenticated (or re-authenticated if required), {project_name} displays a credential offer page. This page presents two ways for the user to claim the credential:

* **QR code** — The user scans the QR code with a wallet application on another device. The QR code encodes an `openid-credential-offer://` URI that the wallet uses to retrieve the credential offer from {project_name}.
* **Offer URL link** — For same-device wallets, the user can click the link directly to open the offer in a wallet application installed on the same device.

.Credential offer page with QR code
image::images/oid4vci/screenshot-aia-credential-offer-qr.png[Credential offer page showing a QR code and an Offer URL link for claiming a verifiable credential, width=650]

The page displays two steps to guide the user:

. Scan the QR code or click the offer URL to claim the credential with a wallet.
. Click *Continue* to proceed with login after the credential has been obtained.

The user can also click *Cancel* to abort the credential offer and return to the application. When the action is admin-initiated (triggered via email link), the cancel button is hidden.

==== Sending a credential offer from the Admin Console

Administrators can send a credential offer to a user by email directly from the Admin Console. This is useful when the administrator wants to proactively issue a credential to a user without requiring the user to initiate the flow from a client application.

===== Prerequisites

* The user must have an email address configured.
* SMTP must be configured for the realm (see <<_email,Configuring email for a realm>>).
* The user must have at least one verifiable credential assigned (see <<_oid4vci_user_setup,Creating a User Account>>).

===== Sending the offer

. In the Admin Console, navigate to *Users* and select the target user.
. Switch to the *Verifiable Credentials* tab. This tab lists the verifiable credentials available to the user.
+
.User Verifiable Credentials tab in the Admin Console
image::images/oid4vci/screenshot-user-verifiable-credentials-tab.png[Admin Console showing the Verifiable Credentials tab for a user with a list of available credentials and a Send credential offer action, width=750]

. Click *Send credential offer* for the credential you want to issue.
. In the dialog that appears, configure the offer lifespan — this determines how long the email link remains valid.
+
.Send credential offer dialog
image::images/oid4vci/screenshot-send-credential-offer-dialog.png[Send credential offer dialog showing a lifespan selector for configuring how long the email link remains valid, width=500]

. Click *Send* to deliver the email.

The user receives an email containing a link. When the user clicks the link, they are taken to the credential offer QR code page described above, where they can scan the QR code or click the offer URL to claim the credential with their wallet. Since this is an admin-initiated action, the cancel button is not shown on the credential offer page.

[NOTE]
====
The email link uses {project_name}'s action token mechanism. The lifespan of the link is configurable in the dialog and defaults to the realm's *Default Admin-Initiated Action Lifespan* setting, which is 12 hours by default. If the link expires before the user clicks it, they will see an error page.
====
