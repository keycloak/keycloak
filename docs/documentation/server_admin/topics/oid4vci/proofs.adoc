[[_oid4vci_proofs]]
=== Proof Types and Key Binding in OID4VCI

A credential proof in OID4VCI is a cryptographic proof-of-possession that a wallet sends to an issuer ({project_name}) to show it controls the private key meant to be
bound to the new credential.

Purposes of the proof are:

* **Anti-replay** - the nonce in the proof prevents a captured credential request from being replayed
* **Key binding** - the public proof key embedded in the VC ties the credential to the Wallet's key pair. When credential is later presented by the wallet to the
credential verifier, verifier is able to cryptographically verify issuer as well as holder/wallet. Verifying of the holder is possible in case that key binding was used.

[[_oid4vci_proofs_use_cases]]
==== Example use cases

===== Use Case 1: Credential request without proof

.Credential request without proof
image::images/oid4vci/proof_part1-no-proof.drawio.svg[Credential request without proof]

. Wallet sends credential request without a `proofs` parameter
. Issuer/{project_name} issues the credential but has no key to bind (for instance, in case of SD-JWT credential format, there is no `cnf` claim)
. Wallet creates the "verifiable credential presentation" and sends it to the verifier. However that presentation does not have key binding (for instance, in case of SD-JWT credential format, presentation ends with `~`)
. Verifier is able to verify issuer signature and eventually disclosed claims digests. However verifier cannot verify holder key binding and hence cannot distinguish the presenter from anyone else who stole the credential.
Risk is, that credential can be replayed or transferred to a different party.

===== Use Case 2: Credential request with non-attested proof

.Credential request with proof
image::images/oid4vci/proof_part2-jwt-proof.drawio.svg[Credential request with proof]

. Wallet fetches `c_nonce` from Issuer's nonce endpoint
. Wallet generates a key pair before credential request (if it does not have existing key pair already). Wallet signs `openid4vci-proof+jwt` (in case that `jwt` proof was used, which is most typical for this use case). JWT header carries public proof key inline (typically in `jwk` claim). The proofs is sent within credential request to the issuer ({project_name})
. Issuer validates proof JWT, extracts public key, embeds into the credential (for instance, in issued SD-JWT format, it is embedded into `cnf.jwk` claim)
. At presentation, Wallet appends a Key-Binding JWT signed with private proof key.
. Thanks to the key binding, verifier is able to verify Key-Binding JWT signature against `cnf.jwk` from issuer signed JWT. This allows to prevent bearer/replay attacks, which is main benefit against use case 1. For more details, see the <<_oid4vci_proofs_key_binding, Key Binding section>>

===== Use Case 3: Credential request with attested proof

Attestation is additional (optional) part of credential proof to add additional security. The purpose is to ensure that the proof key lives in a trusted environment (e.g. hardware secure element). It includes another entity called **Attester**. Attester is an external, trusted party. It participates in the creation of attested credential proofs for the credential wallets.
Attester has trust relationship with the issuer ({project_name}) as issuer should be able to verify attestation.

.Credential request with attested proof
image::images/oid4vci/proof_part3-attested-proof.drawio.svg[Credential request with attested proof]

. Wallet sends its public proof key to the Attester
. Attester checks the key is in a trusted environment (e.g. hardware-backed). Then issues key-attestation JWT signed by attestation private key
. Wallet either sends the key-attestation JWT as an `attestation` proof, or embeds it in the `key_attestation` header of a separate `jwt` proof.
. Issuer validates the attestation JWT against the Attester's public key (registered in Trusted Key IDP); for a `jwt` proof, it also validates the enclosing proof JWT. The public key (or certificate) of the Attester must be configured in {project_name} to establish trust.
. Issuer issues the credential including key-binding and returns to the wallet. It includes the wallet/holder key for the key binding (not the attestation key or attestation certificate)
. Same like step 4 for use case 2
. Same like step 5 for use case 2

The following sections document the proof types supported by OpenID for Verifiable Credential Issuance (OID4VCI), how to configure trusted attester keys, and how key binding works in the resulting credentials.

==== Supported Proof Types

{project_name} currently supports the following proof types for holder binding:

[cols="1,1,2", options="header"]
|===
| Proof Type
| Value
| Description

| JWT Proof
| `jwt`
| A signed JWT containing holder binding information. The key used to sign the JWT becomes the holder binding key in the credential. Supported for both <<_oid4vci_proofs_use_cases,use case 2 and use case 3>>.

| Attestation Proof
| `attestation`
| Proof containing key attestations from a trusted attestation authority. Supported for <<_oid4vci_proofs_use_cases,use case 3>>.
|===

When a credential requires cryptographic holder binding, the client must provide a proof of an appropriate type. The issuer validates the proof and extracts the binding key, which is then included in the issued credential.

[[_oid4vci_proofs_client_scope_config]]
==== Client Scope Configuration for Proof Types

To require key binding for a credential, configure the OID4VCI client scope with the appropriate attributes. These settings are advertised in the issuer metadata as `cryptographic_binding_methods_supported` and `proof_types_supported`, and they determine which proof types the wallet can use.

.Client scope configuration for proofs
image::images/oid4vci/proof_client_scope_config.png[Client scope configuration for proofs]

Most relevant options of the client scope related to proofs and key binding:

* **Cryptographic binding required** - When OFF, proofs are not required in credential request and key binding will not be used for verifiable credentials. This is <<_oid4vci_proofs_use_cases, use case 1 from examples above>>.
When this is ON, proofs are required in credential request and key binding will be used as specified in the <<_oid4vci_proofs_use_cases, use cases 2 and 3 from examples above>>.
If **Cryptographic binding required** is not enabled, the issuer metadata omits `cryptographic_binding_methods_supported` and `proof_types_supported`.

* **Supported proof types** - The attribute accepts a comma-separated list of supported proof types, currently `jwt` and `attestation`.

* **Cryptographic binding methods** - Comma separated list of key binding methods. Typical value is `jwk` for the supported credential formats like SD-JWT format, but might be different according to what particular format supports.

* **Key attestations required** - If ON, then proofs must be always attested as specified in the <<_oid4vci_proofs_use_cases, use case 3 above>>

* **Key storage resistance levels** and **User authentication resistance levels** - If this is configured, the corresponding values must be included in the attestation proofs. Those will be included in the OID4VCI credential metadata. Details about this are in the https://openid.net/specs/openid-4-verifiable-credential-issuance-1_0.html#appendix-D.2[section D.2 of the OID4VCI specification].

NOTE: The `proof_signing_alg_values_supported` values in the metadata are automatically included in the issuer metadata based on the realm's supported asymmetric signing algorithms.

==== Configuring Trusted Attesters

This is needed to be configured for the <<_oid4vci_proofs_use_cases, use case 3 from examples above>>.
{project_name} supports JWT proofs that can optionally include key attestations, and the `attestation` proof type. To validate these attestations, configure the trusted attester keys through trust-material identity providers and link those identity providers to the OID4VCI client.

Trusted attester keys are configured per client because different wallets can rely on different attestation authorities. The former realm-level options **Trusted Key IDs** and **Trusted Keys (JSON)** are no longer used for OID4VCI proof validation.

===== Admin Console

. Create or configure a trust-material identity provider, such as **Default Trust**, that exposes the trusted attester public keys or X.509 trust anchors.
** For `kid`-based attestations, configure a JWKS URL or validating public key.
** For `x5c`-based attestations, enable **Use X.509 attestation trust**, provide a PEM bundle containing only self-signed device-vendor attestation CA roots, and configure **Required extended key usages** with the accepted Extended Key Usage (EKU) OIDs. When at least one OID is configured, the attestation end-entity certificate must contain an EKU extension with at least one OID that exactly matches a configured value; otherwise, validation fails. When the list is empty, no EKU restriction is applied and the trust anchors alone decide trust.
. Go to *Clients* and select the wallet client that requests credentials.
. Open the *Advanced* tab.
. In the *OpenID Verifiable Credentials* section, enable **Enable OID4VCI**.
. In **OID4VCI Attester Trust Identity Providers**, select the trust-material identity providers that contain the trusted attester public keys.
. Save the client.

OID4VCI does not define a universal EKU OID for key attestation. Use the OID specified by the device vendor or the applicable attestation trust framework. For example, a private test PKI could place `1.3.6.1.4.1.32473.1.1` in both the certificate and the configuration to demonstrate exact matching. The `32473` private enterprise number is reserved for documentation and must not be used in production.

WARNING: The built-in OIDC identity provider exposes only JWK trust material and cannot provide X.509 trust anchors for `x5c`-based attestations. Use **Default Trust**, or a custom trust-material identity provider that implements X.509 trust resolution, for `x5c`-based attestations.

WARNING: Certificate revocation checking is not currently supported for `x5c` key-attestation certificate chains. Before trusting an attestation CA, ensure that revoked attestation certificates are rejected by a mandatory revocation mechanism outside {project_name}.

The **OID4VCI Attester Trust Identity Providers** option is only shown when **Enable OID4VCI** is enabled for the client. It accepts only trust-material identity providers from the current realm. If no trust-material identity provider is configured, the dropdown has no values to select.

===== Client Attribute

[cols="1,1,2", options="header"]
|===
| Attribute
| Default
| Description

| `oid4vci.attester_trust_idps`
| none
| Comma-separated aliases of trust-material identity providers containing trusted attester public keys or X.509 attestation roots for OID4VCI key attestation validation.

|===

===== Admin REST API

Use the Admin REST API when you need to configure the client attribute directly.

[source,bash]
----
curl -X PUT "https://localhost:8443/admin/realms/{realm}/clients/{client-uuid}" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
        "attributes": {
          "oid4vci.enabled": "true",
          "oid4vci.attester_trust_idps": "alias-1,alias-2"
        }
      }'
----

For a JWT proof with a `key_attestation` JOSE header, or for an `attestation` proof, {project_name} resolves the attester signing key from the configured identity providers. Key resolution can use the attestation JWT header and payload, including the `kid`, `alg`, and `iss` values. If no configured identity provider trusts the key or certificate chain, proof validation fails.

===== X.509 Certificate-Chain Validation

For an `x5c`-based key attestation, the certificates presented in the attestation JWT and the trust material configured in the identity provider have different roles:

[source,text]
----
Attestation JWT JOSE header                   Default Trust identity provider
---------------------------                   -------------------------------
x5c[0]: attestation leaf certificate          Trusted certificates:
         - signs the attestation JWT            device-vendor root CA
         - must be an end-entity certificate    (self-signed trust anchor)
         - contains an allowed EKU

x5c[1..n]: intermediate CA certificates       Allowed attestation extended
           needed to build the path            key usages:
           (if any)                             device-vendor attestation EKU

x5c[last]: device-vendor root CA              The same root is configured
           (optional)                          as the trust anchor

                    Certificate path built by Keycloak
       attestation leaf -> intermediate CA(s) -> configured root CA
----

The first `x5c` entry must be the certificate containing the public key that signed the attestation JWT. Each following entry must be an issuer of the previous certificate. The entries are base64-encoded DER certificates, not PEM values or base64url-encoded values.

Include any intermediate CA certificates required to connect the leaf to the configured root. The root certificate can be the final `x5c` entry, but it is not required because the same root is already configured as a trust anchor. For example, if the configured root directly issued the leaf, `x5c` can contain only the leaf certificate.

For each selected X.509-capable trust-material identity provider, {project_name} independently builds a certificate path from the leaf to a root configured in that provider. The leaf must be an end-entity certificate, and its Extended Key Usage (EKU) extension must contain at least one OID allowed by the same provider. Trust roots and EKU policies from different providers are never combined.

A root included in `x5c` does not become trusted merely by being present. It must match a root configured in the identity provider. The JVM system truststore is never used as attestation trust.

Do not place public Web PKI roots or the general {project_name} TLS truststore in an attestation trust provider. Each provider should represent one device-vendor trust domain so its roots and certificate policy cannot be combined with another provider accidentally.

==== Creating and Sending JWT Proofs

JWT proofs are the most common proof type. They support the <<_oid4vci_proofs_use_cases, use cases 2 and 3 from examples above>>. The following steps describe creation of a JWT proof without attestation (use case 2):

===== 1. Obtain a Nonce

First, call the nonce endpoint to obtain a fresh nonce:

[source,bash]
----
curl -X POST "https://localhost:8443/realms/{realm}/protocol/oid4vc/nonce" \
  -H "Authorization: Bearer $ACCESS_TOKEN"
----

Response:
[source,json]
----
{
  "c_nonce": "abc123def456...",
  "c_nonce_expires_in": 300
}
----

===== 2. Create the JWT Proof

The JWT proof must contain the following claims:

[cols="1,1,2", options="header"]
|===
| Claim
| Required
| Description

| `iss`
| Conditional
| For client-bound flows, must be the client_id. For anonymous flows, omit this claim.

| `aud`
| Yes
| Must be the Credential Issuer Identifier of the issuing realm

| `nonce`
| Yes
| The c_nonce value obtained from the nonce endpoint.

| `iat`
| Yes
| Issued-at time (Unix timestamp). Must be within 30 seconds of server time.

| `exp`
| No
| Expiration time. If provided, must be in the future.

| `nbf`
| No
| Not-before time. If provided, must be before server time + 10 seconds.
|===

.Header Requirements
[cols="1,2", options="header"]
|===
| Header
| Description

| `typ`
| Must be `openid4vci-proof+jwt`

| `alg`
| One of the algorithms listed in `proof_signing_alg_values_supported` (e.g., `ES256`, `RS256`, `PS256`)

| `jwk` or `kid` or `x5c`
| The binding key. Only one of these should be present.
|===

====== Example: JWT Proof with JWK in Header

[source,javascript]
----
// Header
{
  "typ": "openid4vci-proof+jwt",
  "alg": "ES256",
  "jwk": {
    "kty": "EC",
    "crv": "P-256",
    "x": "f83OJ3B2f4GuoXv...d83rVU",
    "y": "X_5R34qL2Y8ZdqU..."
  }
}

// Payload
{
  "iss": "your-client-id",
  "aud": "https://localhost:8443/realms/myrealm",
  "nonce": "abc123def456...",
  "iat": 1719785014
}
----

====== Example: JWT Proof with kid Header

[source,javascript]
----
// Header
{
  "typ": "openid4vci-proof+jwt",
  "alg": "ES256",
  "kid": "my-binding-key-id"
}

// Payload
{
  "iss": "your-client-id",
  "aud": "https://localhost:8443/realms/myrealm",
  "nonce": "abc123def456...",
  "iat": 1719785014
}
----

===== 3. Send the Credential Request

Include the JWT proof in the credential request:

[source,json]
----
{
  "format": "jwt_vc_json",
  "credential_configuration_id": "my-credential-config",
  "proofs": {
    "jwt": ["eyJhbGciOiJFUzI1NiIsInR5cCI6Im9wZW5pZDh2Y2ktcHJvb2Yrand0IiwiandrIjp7Imt0eSI6IkVDIiwiY3J2IjoiUC0yNTYiLCJ4IjoiZjgzak8zQjJmNFdndU...=="]
  }
}
----

==== Using Attestation Proofs

Attestation proofs allow the holder to prove key ownership through an attestation authority. This is useful for hardware-backed keys or keys managed by secure enclaves.
The example is described in the <<_oid4vci_proofs_use_cases, use case 3 from examples above>>.

===== Structure of an Attestation Proof

An attestation proof is a JWT containing:

.Header
[cols="1,2", options="header"]
|===
| Header
| Description

| `typ`
| `openid4vci-attestation+jwt`

| `kid`
| Key ID of the attestation signing key

| `alg`
| Algorithm (e.g., `ES256`)
|===

.Payload
[cols="1,1,2", options="header"]
|===
| Claim
| Required
| Description

| `nonce`
| Yes
| The c_nonce from the nonce endpoint

| `iat`
| Yes
| Issued-at time

| `exp`
| Yes
| Expiration time

| `attested_keys`
| Yes
| Array of JWK objects representing the holder's attested keys

| `key_storage`
| No
| List of acceptable key storage attack potential levels (ISO 18045)

| `user_authentication`
| No
| List of acceptable user authentication attack potential levels

| `status`
| Yes
| Object with `status` claim (e.g., `{"status": "valid"}`)
|===

===== Credential Request with Attestation Proof

[source,json]
----
{
  "format": "jwt_vc_json",
  "credential_configuration_id": "my-credential-config",
  "proofs": {
    "attestation": ["eyJhbGciOiJFUzI1NiIsInR5cCI6Im9wZW5pZDh2Y2ktYXR0ZXN0YXRpb24rand0Ii...=="]
  }
}
----

[[_oid4vci_proofs_key_binding]]
==== Key Binding in Credentials

The binding key from the proof is included in the issued credential to ensure the holder possesses the corresponding private key.

===== JWT VC JSON Format

For `jwt_vc_json` format credentials, the binding key is included in the `cnf` (confirmation) claim:

[source,json]
----
{
  "iss": "https://localhost:8443/realms/myrealm",
  "vc": {
    "@context": ["https://www.w3.org/2018/credentials/v1"],
    "type": ["VerifiableCredential", "MyCredential"],
    "credentialSubject": { ... },
    "cnf": {
      "jwk": {
        "kty": "EC",
        "crv": "P-256",
        "x": "f83OJ3B2f4GuoXv...d83rVU",
        "y": "X_5R34qL2Y8ZdqU..."
      }
    }
  },
  "iat": 1719785014,
  "exp": 1751321014,
  "jti": "unique-credential-id"
}
----

===== SD-JWT Format

For `dc+sd-jwt` format credentials, the binding key is included as a disclosure in the SD-JWT:

[source]
----
eyJhbGciOiJFUzI1NiJ9.eyJAY29udGV4dCI6WyJodHRwczovL3d3dy53My5vcmcvMjAxOC9jcmVkZW50aWFscy92MSJdLCJ0eXBlIjpbIlZlcmlmaWFibGVDcmVkZW50aWFsIiwiTXlDcmVkZW50aWFsIl0sImNyZWRlbnRpYWxTdWJqZWN0Ijp7fSwiY25mIjp7Imp3ayI6eyJrdHkiOiJFQyIsImNydiI6IlAtMjU2IiwieCI6ImY4M09PM0IyZjRHZ3VYdi4uLmQ4M3JWVSJ9fX0.K3ZkVYZ2B9...#eyJjdHgiOnsidHlwZSI6ImNuZiIsIm9iaiI6eyJrdHkiOiJFQyIsImNydiI6IlAtMjU2In19"
----

The holder binding key appears in the `_sd_hash` of the SD-JWT, allowing verifiers to confirm the holder possesses the corresponding private key.

===== Verifying Key Binding

When presenting a credential, the verifier should:

1. Extract the `cnf` claim (for JWT VC) or verify the `_sd_hash` (for SD-JWT)
2. Challenge the holder to sign a challenge with the corresponding private key
3. Verify the signature matches the bound key

==== Complete Example: Credential Request with JWT Proof

[source,bash]
----
# 1. Get an access token (OAuth2 flow)
# ... (obtain access token with appropriate scopes)

# 2. Obtain nonce
NONCE_RESPONSE=$(curl -X POST "https://localhost:8443/realms/myrealm/protocol/oid4vc/nonce" \
  -H "Authorization: Bearer $ACCESS_TOKEN")
C_NONCE=$(echo $NONCE_RESPONSE | jq -r '.c_nonce')

# 3. Create JWT proof (pseudocode - use your JWT library)
PROOF_HEADER='{ "typ":"openid4vci-proof+jwt", "alg":"ES256", "jwk":{ "kty":"EC", "crv":"P-256", "x":"...", "y":"..." } }'
PROOF_PAYLOAD="{ \"iss\":\"your-client-id\", \"aud\":\"https://localhost:8443/realms/myrealm\", \"nonce\":\"$C_NONCE\", \"iat\":$(date +%s) }"
JWT_PROOF=$(create_jwt "$PROOF_HEADER" "$PROOF_PAYLOAD" "$YOUR_PRIVATE_KEY")

# 4. Send credential request
curl -X POST "https://localhost:8443/realms/myrealm/protocol/oid4vc/credential" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "format": "jwt_vc_json",
    "credential_configuration_id": "my-credential-config",
    "proofs": {
      "jwt": ["'"$JWT_PROOF"'"]
    }
  }'
----

Additional working examples on how to setup and use proofs can be seen from the https://github.com/keycloak/keycloak-playground/blob/main/fapi-playground/README.md#oid4vci-demo[Keycloak playground repository] (not officially supported repository).
