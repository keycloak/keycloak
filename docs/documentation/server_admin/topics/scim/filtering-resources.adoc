[[_scim_filtering_resources]]
= Filtering resources
[role="_abstract"]

The SCIM API in {project_name} supports the full filter syntax defined in https://datatracker.ietf.org/doc/html/rfc7644#section-3.4.2.2[RFC 7644, Section 3.4.2.2],
allowing you to search for resources using a rich expression language.

== Using filters

Filters are specified using the `filter` query parameter on `GET` requests:

[source,bash]
----
curl "http://localhost:8080/realms/myrealm/scim/v2/Users?filter=userName+eq+\"jdoe\"" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Accept: application/scim+json"
----

NOTE: Filter values must be URL-encoded when used in query parameters. Spaces in the filter expression should be
encoded as `+` or `%20`. The examples in this section show the raw filter syntax for readability.

== Comparison operators

The following comparison operators are supported:

[cols="1,2,3",options="header"]
|===
| Operator | Description | Example

| `eq`
| Equal
| `userName eq "jdoe"`

| `ne`
| Not equal
| `active ne false`

| `co`
| Contains
| `emails co "example.com"`

| `sw`
| Starts with
| `userName sw "j"`

| `ew`
| Ends with
| `userName ew "doe"`

| `gt`
| Greater than
| `meta.created gt "2025-01-01T00:00:00Z"`

| `ge`
| Greater than or equal
| `meta.created ge "2025-01-01T00:00:00Z"`

| `lt`
| Less than
| `meta.lastModified lt "2025-06-01T00:00:00Z"`

| `le`
| Less than or equal
| `meta.lastModified le "2025-06-01T00:00:00Z"`

| `pr`
| Present (attribute has a value)
| `emails.value pr`
|===

NOTE: The `gt`, `ge`, `lt`, and `le` operators are supported on date/time attributes such as `meta.created` and
`meta.lastModified`. The `sw`, `ew`, and `co` operators are supported on string attributes but not on date/time
or boolean attributes. Invalid operator/type combinations return a `400 Bad Request` response with
`scimType: "invalidFilter"`.

[[_scim_filtering_null_values]]
== Attributes without a value

Filters are evaluated in the database, and whether a resource whose attribute has no value is returned depends on how
{project_name} stores the attribute:

* *Stored with the resource.* For users, these are `userName`, `name.givenName`, `name.familyName`, `emails`,
`active`, `meta.created`, and `meta.lastModified`. For groups, these are `displayName`, `meta.created`, and
`meta.lastModified`. A comparison with a missing value is neither true nor false, so neither the comparison nor its
negation returns the resource.
* *Stored as separate values.* These are all other attributes, including the remaining core attributes such as
`title` or `externalId`, extension and custom attributes, `groups.value`, and `members.value`. A comparison is true
only when a matching value exists, so `ne` does not return a resource without a value, but a negated `eq` does. For a
multi-valued attribute, `ne` returns the resources that have at least one other value.

The following table shows whether a resource without a value for `attribute` is returned:

[cols="2,1,1",options="header"]
|===
| Filter | Stored with the resource | Stored as separate values

| `attribute ne "value"`
| Not returned
| Not returned

| `not (attribute eq "value")`
| Not returned
| Returned

| `not (attribute pr)`
| Returned
| Returned

| `attribute eq null` or `attribute ne null`
| Never matches
| Never matches
|===

The `eq` and `ne` operators accept the `null` literal, but the comparison never matches, so it cannot be used to find
resources without a value.

== Logical operators

Filters can be combined using logical operators:

[cols="1,3",options="header"]
|===
| Operator | Description

| `and`
| Both conditions must be true.

| `or`
| At least one condition must be true.

| `not`
| Negates the following expression. Parentheses are optional but recommended for clarity.
|===

=== Examples

Filter users by family name and active status:

----
name.familyName eq "Smith" and active eq true
----

Filter users matching either condition:

----
userName eq "jdoe" or userName eq "asmith"
----

Negate a condition:

----
not (active eq false)
----

Use parentheses to group conditions:

----
(userName sw "j" or userName sw "a") and active eq true
----

== Filtering by sub-attributes

You can filter by sub-attributes of complex attributes using dot notation:

----
name.givenName eq "John"
name.familyName sw "Sm"
----

For multi-valued attributes like `emails`:

----
emails eq "jdoe@example.com"
emails.value eq "jdoe@example.com"
emails co "example.com"
----

== Value path filters

SCIM also supports value path filtering, where you filter on sub-attributes within a complex attribute using
bracket notation:

----
name[familyName eq "Smith"]
name[givenName eq "John" and familyName eq "Doe"]
name[givenName eq "John" or givenName eq "Jane"]
----

Value path filters can be combined with regular filters:

----
name[familyName eq "Smith"] and active eq true
----

== Filtering by group membership

You can filter users by their group membership using the `groups.value` attribute:

[source,bash]
----
curl "http://localhost:8080/realms/myrealm/scim/v2/Users?filter=groups.value+eq+\"{groupId}\"" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Accept: application/scim+json"
----

Combine group membership filters with logical operators:

----
(groups.value eq "{groupIdA}") and (groups.value eq "{groupIdB}")
(groups.value eq "{groupIdA}") or (groups.value eq "{groupIdB}")
----

Similarly, you can filter groups by member:

[source,bash]
----
curl "http://localhost:8080/realms/myrealm/scim/v2/Groups?filter=members.value+eq+\"{userId}\"" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Accept: application/scim+json"
----

NOTE: When fine-grained admin permissions (FGAP) are enabled, only the `eq` operator is supported for
`groups.value` and `members.value` filter paths. The server verifies that the caller has `view` permission
on the specific group or user being matched. Other operators (`ne`, `pr`, `co`, `sw`, `gt`, etc.) cannot be
safely authorized because they can match rows the caller is not permitted to see, so they silently return
empty results for these paths. For the same reason, negating an equality condition on these paths (for example,
`not (groups.value eq "{groupId}")`) also returns empty results, because it is equivalent to the unsupported
`ne` operator. This restriction does not apply to any other filter attributes, and does not apply when FGAP is
disabled, where the full set of operators is available on these paths.

NOTE: When an LDAP user federation provider is configured with a group mapper in `LDAP_ONLY` mode, group
membership filters (`groups.value` and `members.value`) may return empty results. This happens because
`LDAP_ONLY` mode stores group memberships exclusively in LDAP, while the SCIM filter queries the local
database directly. Retrieving a user's groups via `?attributes=groups` or a group's members via
`?attributes=members` is not affected, as those requests go through the federation layer and read from LDAP.
If you need membership-based filtering with LDAP federation, consider switching the group mapper to `IMPORT`
mode so that memberships are also stored locally.

== Filtering by extension attributes

Filters can reference attributes from schema extensions by using the full schema URI as a prefix:

----
urn:ietf:params:scim:schemas:extension:enterprise:2.0:User:department eq "Engineering"
urn:ietf:params:scim:schemas:extension:enterprise:2.0:User:manager.displayName ew "Manager"
----

For custom schema extensions:

----
urn:my:params:scim:schemas:extension:custom:1.0:User:myattribute eq "myvalue"
----

See <<_scim_managing_schema_extensions_,Managing schema extensions>> for more details on configuring extension attributes.

== Using POST-based search

For complex queries that might exceed URL length limitations, use the `POST /.search` endpoint:

[source,bash]
----
curl -X POST http://localhost:8080/realms/myrealm/scim/v2/Users/.search \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Content-Type: application/scim+json" \
  -d '{
    "schemas": ["urn:ietf:params:scim:api:messages:2.0:SearchRequest"],
    "filter": "(userName sw \"j\" or userName sw \"a\") and active eq true",
    "startIndex": 1,
    "count": 10,
    "attributes": ["userName", "emails"]
  }'
----

The search request body supports the same parameters available as query parameters: `filter`, `startIndex`,
`count`, `attributes`, `excludedAttributes`, `sortBy`, and `sortOrder`.

== Pagination

When listing or searching resources, you can control the page of results returned using the `startIndex` and
`count` parameters:

[source,bash]
----
curl "http://localhost:8080/realms/myrealm/scim/v2/Users?startIndex=1&count=10" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Accept: application/scim+json"
----

The response includes pagination metadata:

[source,json]
----
{
  "schemas": ["urn:ietf:params:scim:api:messages:2.0:ListResponse"],
  "totalResults": 45,
  "itemsPerPage": 10,
  "startIndex": 1,
  "Resources": [...]
}
----

*   `totalResults`: The total number of resources matching the query.
*   `itemsPerPage`: The number of resources in the current page.
*   `startIndex`: The 1-based index of the first resource in the current page.

To retrieve the next page, increment `startIndex` by `count`:

[source,bash]
----
curl "http://localhost:8080/realms/myrealm/scim/v2/Users?startIndex=11&count=10" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H "Accept: application/scim+json"
----

== Filtering constraints and limitations

Keep the following constraints in mind when building filter expressions. These are intended behaviors and should not be
reported as defects.

* *Result size is capped.* A list or search request returns at most 100 results. If `count` is omitted or greater
than 100, it is treated as 100 (`filter.maxResults`). Use pagination (see <<Pagination>>) to retrieve additional results.
* *Filter length is limited.* A filter expression may not exceed 2048 characters. Longer expressions are rejected with a
`400 Bad Request` and `scimType: "invalidFilter"`.
* *Nesting depth is limited.* The combined nesting of grouping parentheses and value path brackets may not exceed 10
levels. Deeper expressions are rejected with a `400 Bad Request` and `scimType: "invalidFilter"`.
* *Sorting is not applied.* The `sortBy` and `sortOrder` parameters are accepted but ignored. Results are returned in the
default order of the underlying store, consistent with the {project_name} Admin REST API.
* *The `and` operator cannot be used to match multiple values within the same multivalued array.* For example,
`groups[value eq "{groupIdA}" and value eq "{groupIdB}"]` is rejected because a single group element cannot have two values
simultaneously. Use `or` to match either value.
* *Operator and attribute-type compatibility is enforced.* String operators (`sw`, `ew`, `co`) cannot be used on
date/time or boolean attributes, and incompatible combinations are rejected. See <<Comparison operators>>.
* *Comparisons skip attributes without a value.* `attribute ne "value"` and `attribute eq null` do not match resources
where the attribute has no value. Use `not (attribute pr)` to find them. See <<Attributes without a value>>.
* *Membership filters carry extra restrictions.* The `groups.value` and `members.value` paths behave differently under
fine-grained admin permissions and with LDAP `LDAP_ONLY` group mappers. See <<Filtering by group membership>>.

== Error responses

Invalid filter expressions return a `400 Bad Request` response with `scimType: "invalidFilter"`:

[source,json]
----
{
  "schemas": ["urn:ietf:params:scim:api:messages:2.0:Error"],
  "scimType": "invalidFilter",
  "detail": "Invalid filter expression",
  "status": "400"
}
----

Common causes of filter errors:

*   Mismatched parentheses.
*   Unknown filter operators.
*   Using an operator on an incompatible attribute type (for example, `gt` on a boolean).
*   Using string operators (`sw`, `ew`, `co`) on date/time attributes.
*   Using `null` with an operator other than `eq` or `ne`.
