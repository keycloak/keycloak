// ------------------------ Breaking changes ------------------------  //
== Breaking changes

Breaking changes are identified as those that might require changes for existing users to their configurations or applications.
In minor or patch releases, {project_name} will only introduce breaking changes to fix bugs.

=== Realm client session statistics respect client visibility
// https://github.com/keycloak/keycloak/issues/50917

The Admin REST API endpoint `GET /admin/realms/\{realm}/client-session-stats` now returns online and offline session statistics only for clients the caller is allowed to view.
It continues to require the `view-realm` or `manage-realm` role.
Previously, either realm role allowed callers to retrieve statistics for clients they could not view.
After upgrading, such callers receive fewer entries, or an empty list if no clients with sessions are visible to them.

Client visibility follows the same permission checks as the client-specific session count endpoints across RBAC, fine-grained admin permissions v1, and v2:

* The `view-clients` and `manage-clients` admin roles grant visibility to all clients.
* Fine-grained admin permissions v1 grant client visibility through the `view`, `configure`, or `manage` permission.
* Fine-grained admin permissions v2 keep the Clients `view` and `manage` scopes independent. When access is granted only through fine-grained permissions, `manage` alone does not grant visibility.

Counts for visible clients continue to include all their sessions, independently of the caller's permission to view the associated users.

=== SAML back-channel SLO via SessionIndex requires client signature
// https://github.com/keycloak/keycloak/issues/53535

Back-channel SAML single logout that identifies the session with `SessionIndex` (no browser cookie) now requires the initiating client to have *Client signature required* (`saml.client.signature`) enabled.
Without a verified signature, the `Issuer` field is not authenticated and could be forged to terminate another client's session.

Browser-based (front-channel) logout that carries the user's SSO cookie is unchanged and still works for clients that do not require signatures.

If a SAML client uses back-channel SLO with `SessionIndex` and has *Client signature required* set to *OFF*, either:

* Enable *Client signature required* and configure the client's signing certificate, then sign `LogoutRequest` messages, or
* Prefer front-channel logout so the browser cookie authenticates the request.

Newly created SAML clients already default to requiring client signatures. Deployments that import realm JSON may still have unsigned clients and are the primary group affected by this change.

=== The `admin-permissions` client is treated as an internal client
// https://github.com/keycloak/keycloak/issues/51630

When fine-grained admin permissions V2 are enabled on a realm, the `admin-permissions` client holds the whole authorization model of that realm.
This client is now treated as an internal client, the same way the `realm-management` client already is, so it can no longer be managed through the Admin REST API.
Previously, an administrator with a *manage* permission on clients could update it, including changing its `clientId`, even though the `access.manage` field returned for the client was already `false`.

After upgrading, requests that update the `admin-permissions` client are rejected with a 403 status.
Requests that delete it are also rejected with a 403 status, where previously they were rejected with a 400 status.
Configuring the permissions and the policies of the realm is not affected, as it requires the `manage-realm` role rather than a permission on the client.

=== User storage periodic sync runs at the configured period again

Periodic full and changed-users synchronization for a user storage provider now starts every `fullSyncPeriod` or `changedSyncPeriod` seconds, as documented.
A regression caused a sync to run only on every other scheduled tick, so the effective interval was about twice the configured period, whenever a single sync took longer than roughly one second.
The provider's last-sync time is now recorded when a sync starts rather than when it finishes, so the schedule no longer drifts by the sync duration.

If you previously lowered `fullSyncPeriod` or `changedSyncPeriod` to compensate for the doubled interval, review those values.
