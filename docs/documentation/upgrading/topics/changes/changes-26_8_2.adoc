== Breaking changes

Breaking changes are identified as those that might require changes for existing users to their configurations or applications.
In minor or patch releases, {project_name} will only introduce breaking changes to fix bugs.

=== Protocol mapper management restricted to realm administrators
// https://github.com/keycloak/keycloak/issues/1198

By default, protocol mapper create, update, and delete operations on clients and client scopes through the Admin REST API now require the
caller to have permission to manage the realm.
Previously, a delegated administrator with only permission to manage clients could create or update protocol mappers on
clients and client scopes, which allowed a privilege-escalation path where admin roles or other sensitive claims could be
mapped into tokens or assertions.

After upgrading, any callers that create, update, or delete protocol mappers on clients or client scopes through the Admin
REST API must have realm management permission — for example, by holding the `manage-realm` role when role-based access
control is used — unless explicitly delegated.

If a realm administrator wants delegated administrators with permissions to manage clients (or client scopes) to be able to
create, update, or delete protocol mappers, they must specify the allowed protocol mapper types in the **Allowed protocol mapper types for client administrators**
option. In the admin console, this is located in the **Realm settings** tab of the particular realm. If this list is empty (which is the default),
client administrators cannot manage any protocol mappers.

=== Allowed Protocol Mapper Types restricted in Client Registration Policies
// https://github.com/keycloak/keycloak/issues/1198

As part of the same security fix, the permitted protocol mappers during OpenID Connect Dynamic Client Registration (DCR) client CRUD operations are now restricted.

While the default *Client Registration Policies* (both the *Anonymous* and *Authenticated* registration contexts) still contain the standard list of built-in mapper types (such as user property, user attribute, address, full name, pairwise subject, and SAML role list mappers) in their *Allowed Protocol Mapper Types* list, they are not sufficient by default.

After upgrading, the allowed protocol mappers for DCR operations are the **intersection** of the realm-level **Allowed protocol mapper types for client administrators** option
and the policy-level *Allowed Protocol Mapper Types* list. Since the realm-level option is empty by default, new clients cannot include protocol mappers and DCR updates
cannot add, modify, or delete protocol mappers, until the realm administrator explicitly configures the permitted mapper types in the realm settings. Existing mappers
of a disallowed type may still be included unchanged in an update.

WARNING: Before adding mapper types to either configuration, carefully evaluate the security implications. Allowing protocol mapper creation
via DCR effectively grants the registering party the ability to shape token claims. Only add mapper types that are
absolutely required, and prefer managing protocol mappers through the Admin Console under a fully privileged realm
administrator account.

If you rely on Dynamic Client Registration to register clients with protocol mappers, review the mappers that your
registration flow requires and add only those specific mapper types to BOTH the policy in *Clients* >
*Client Registration* and the *Allowed protocol mapper types for client administrators* option in *Realm Settings*.

=== Admin REST API now enforces an audience check

To align with the OAuth 2.0 security recommendations (RFC 9700), the Admin REST API now verifies that bearer access tokens were issued specifically for the Admin API.
Previously, any access token was accepted regardless of its intended audience, as long as its subject had administrative access to the target realm, whether granted through realm admin roles or Fine-Grained Admin Permissions.

A new built-in client scope, `kc-admin-api`, provides this capability. The scope adds the realm's Admin REST API base URL (for example, `+https://auth.example.com/admin/realms/my-realm+`, resolved from the configured frontend URL)
as an audience to the tokens issued for clients that have the scope.
The Admin REST API now requires the token to both carry this audience and include the `kc-admin-api` scope, so access is tied to this specific built-in scope rather than to any token that happens to carry a matching audience.
On upgrade, this client scope is created in every realm and assigned as a default client scope to the built-in clients used to access the Admin API (`admin-cli` and `security-admin-console`), so out-of-the-box access keeps working.

If you use your own clients and service accounts to obtain tokens for the Admin REST API, you must assign the `kc-admin-api` client scope to those clients (as a default or optional scope). Otherwise, their tokens will be rejected with a `401 Unauthorized` response.

You can disable this check by setting `--spi-admin--audience-check-enabled=false`. Disabling the check is strongly discouraged, as it removes an important layer of defense against token misuse.

During rolling upgrades, old cluster nodes without the Admin API audience mapper would issue admin tokens lacking the required audience attribute.
These tokens would be rejected with `401` errors when routed to upgraded nodes that enforce the audience check.

=== Limit size of InputStream on SOAP endpoints

All SAML SOAP binding endpoints introduced size limit (120000 bytes) on the request to prevent server resources exhaustion. This might prevent current {project_name} server operation.

If you want to increase/decrease this limit, start the server with the option `spi-login-protocol--saml--max-soap-message-request-size`.

.Increasing limit to 512KB
[source,bash]
----
bin/kc.[sh|bat] --spi-login-protocol--saml--max-soap-message-request-size=524288
----

For information see the `login-protocol` provider configuration in the link:{allproviderconfigguide_link}[{allproviderconfigguide_name}].

=== SAML identity broker requires a valid bearer subject confirmation

An assertion consumed by the SAML identity broker must now contain at least one `<SubjectConfirmation>` using the `bearer` method (`urn:oasis:names:tc:SAML:2.0:cm:bearer`) that validates successfully, including a `<SubjectConfirmationData>` element as required by the SAML V2.0 Web Browser SSO Profile.
{project_name} now rejects the login when the assertion carries no such bearer confirmation, for example when it only declares an unsupported method such as holder-of-key (`urn:oasis:names:tc:SAML:2.0:cm:holder-of-key`), or when the bearer confirmation has no `<SubjectConfirmationData>`.

Previously, when no bearer confirmation was present, subject confirmation validation was skipped and the assertion was accepted.
Because {project_name} cannot verify non-bearer confirmation methods (holder-of-key requires proof of possession of the bound key), accepting such assertions could let a proof-of-possession assertion be replayed as a bearer credential.

If you rely on {project_name} brokering an upstream identity provider, make sure that provider issues assertions with a bearer `<SubjectConfirmation>`, which is required by the SAML V2.0 Web Browser SSO Profile.
{project_name} does not support a subject confirmation method other than `urn:oasis:names:tc:SAML:2.0:cm:bearer`.

=== SAML identity broker now rejects assertions with a ProxyRestriction condition

When {project_name} acts as a SAML identity broker, it consumes the assertion issued by the upstream identity provider and issues a new assertion to the downstream client.
An assertion carrying a `<ProxyRestriction>` condition asks the receiving party to enforce a restriction on further assertion issuance. {project_name} does not support this condition, so it
now rejects any incoming assertion that contains a `<ProxyRestriction>` condition instead of brokering it. Assertions that do not carry a `<ProxyRestriction>` condition continue to be accepted.

Previously, the `<ProxyRestriction>` condition was parsed but never enforced, so these assertions were accepted contrary to the SAML 2.0 specification.

This behavior is controlled by a new *Reject proxy restriction* switch on the SAML Identity Provider settings, which is enabled by default.
If you rely on {project_name} brokering assertions from an upstream identity provider that sets a `<ProxyRestriction>` condition, disable this switch on the corresponding Identity Provider to keep accepting those assertions.
Note that {project_name} does not fully support `<ProxyRestriction>`: when the switch is disabled, the condition is ignored and is not propagated to the assertion issued to the downstream client, without any security validation.

=== SAML adapter now validates IdP issuer in responses and logout requests
// https://github.com/keycloak/keycloak-private/issues/1181

The Keycloak SAML adapter now validates that the `Issuer` element in SAML responses, assertions, and logout requests
matches the IdP entity ID configured in the adapter's `keycloak-saml.xml` (the `entityID` attribute on the `<IDP>`
element). Previously, the adapter verified signatures, audience, recipient, and time conditions but did not check
whether the assertion actually came from the expected identity provider.

Additionally, the adapter installation endpoints (`KeycloakSamlClientInstallation` and
`KeycloakSamlSubsystemCliInstallation`) now generate the actual realm URL as the IdP entity ID instead of the
hardcoded placeholder `idp`.

After upgrading, existing adapter configurations that use `entityID="idp"` (or any value that does not match the
realm URL returned by the Keycloak server) must be updated. The correct value is the realm base URL, for example
`http://localhost:8080/realms/myrealm`. The easiest way to obtain the correct value is to re-download the adapter
configuration from the Keycloak Admin Console (*Clients* > *your-saml-client* > *Installation*).

If the `entityID` in your adapter configuration does not match the issuer sent by the Keycloak server, SAML login
and logout will fail with an extraction failure error.

=== Tokens issued by the standard token exchange cannot outlive the subject token

Previously, the `exp` claim of the access token and the ID token issued by the standard token exchange was computed from the request time and the configured access token lifespan, with no relation to the `subject_token`, so a requester client could exchange each issued token again before it expired and extend the lifetime of the identity indefinitely. Starting with this release, the `exp` claim of both tokens is capped by the `exp` claim of the `subject_token`, and `expires_in` is reduced accordingly.

To restore the previous behavior, enable the new switch *Allow exchange token expiration after subject token expiration* on the requester client, in the *OpenID Connect Compatibility Modes* section of the *Advanced* tab, or set the `standard.token.exchange.allowTokenExpirationAfterSubjectTokenExpiration` client attribute. Keeping it off is recommended.

The cap applies to access and ID tokens only. Refresh tokens are controlled by the separate switch *Allow refresh token in Standard Token Exchange*, which is unchanged.

WARNING: With *Allow exchange token expiration after subject token expiration* off and *Allow refresh token in Standard Token Exchange* on, the access token expiration can still be increased indirectly: the requester client exchanges for a refresh token, which is not capped, and refreshes it for an access token with the regular lifespan.

See the link:{securing_apps_token_exchange_link}#_standard-token-exchange-expiration[{securing_apps_token_exchange_name}] for more information.

=== Stricter CIBA request validation

{project_name} now treats the following names as reserved internal authentication request claims for Client Initiated Backchannel Authentication (CIBA) requests:
`sub`, `iss`, `aud`, `azp`, `jti`, `exp`, `iat`, `nbf`, `typ`, and `auth_result_id`.
A CIBA request that supplies any of these names as a standalone form parameter is now rejected with an `invalid_request` error.
Signed authentication request objects supplied through `request` or `request_uri` can contain required JWT claims such as `iss`, `aud`, `exp`, `iat`, `nbf`, and `jti`.
All reserved names are excluded from the additional parameters copied into the internal authentication request, preventing both overwrites of existing claims and assignment to initially unset claims during deserialization.
This filtering does not replace signature verification or JWT claim validation.
Signature verification is performed for signed requests; additional checks of the issuer, audience, and validity period are performed when an applicable client policy enables the `secure-ciba-signed-authn-req` executor.

If your client uses these names for application-specific data, rename those parameters and update any custom authentication channel that consumes them.
Continue to include protocol claims required by signed authentication request objects.

Before issuing a new `auth_req_id`, {project_name} also validates that additional claims with non-null values retain their names after serialization and deserialization.
Additional claims with null values are omitted during serialization and do not cause validation to fail.
Requests that fail this validation are rejected before an authentication channel request is sent.
Custom extensions must not add additional claims that become internal authentication request properties during deserialization, even if those properties are initially unset and no duplicate JSON claim names are produced.

These checks apply to new authentication requests. They do not add duplicate-claim validation when redeeming previously issued `auth_req_id` values.

=== Client registration policies restrict default roles and full scope (CVE-2026-109081)
// https://github.com/keycloak/keycloak-private/issues/1194

Dynamic Client Registration can no longer change the realm-wide default-role composite through the deprecated `defaultRoles` field, and authenticated registration can no longer enable `fullScopeAllowed`, unless a realm administrator removes the corresponding client registration policies.

Starting with this release:

* A *Default Roles Disabled* client registration policy is added to both the anonymous and authenticated client registration policies (including during migration of existing realms).
While this policy is present, create or update requests that would add, change, or remove roles in the realm `default-roles-<realm>` composite through `defaultRoles` are rejected with HTTP `403 Forbidden`.
* The existing *Full Scope Disabled* policy (`scope`) is also added to the authenticated client registration policies (it was already present for anonymous registration).
Newly registered clients through authenticated Dynamic Client Registration have `fullScopeAllowed` disabled, and updates that try to enable it are rejected with HTTP `403 Forbidden`.

Realm administrators who intentionally want Dynamic Client Registration to manage these settings can remove the corresponding policies under *Clients* -> *Client registration* -> *Client registration policies*.
Removing them restores the previous behavior and should be done only when the security implications are understood.
Use the Admin REST API to manage realm default roles and full scope when the policies remain in place.

This migration installs a new client registration policy provider that earlier 26.8.x nodes do not know.
A rolling upgrade is therefore not supported for this change; shut down the cluster and upgrade all nodes together (or use a recreate update) so that older nodes never process Dynamic Client Registration requests against the new policy components.

=== Auto-linking requires a trusted email (CVE-2026-97175)

Identity provider auto-linking now blocks the link when the IdP email is not verified and *Trust Email* is not enabled on the identity provider.
This prevents an attacker who controls a brokered account with an unverified email from being automatically linked to a victim's existing consumer account.

If you use auto-link flows with a SAML or custom identity provider that does not set the `email_verified` claim, enable *Trust Email* on that identity provider to preserve the previous behavior.

=== Realm client session statistics respect client visibility
// https://github.com/keycloak/keycloak/issues/50917

The Admin REST API endpoint `GET /admin/realms/\{realm}/client-session-stats` now returns online and offline session statistics only for clients the caller is allowed to view.
It continues to require the `view-realm` or `manage-realm` role.
Previously, either realm role allowed callers to retrieve statistics for clients they could not view.
After upgrading, such callers receive fewer entries, or an empty list if no clients with sessions are visible to them.

Client visibility follows the same permission checks as the client-specific session count endpoints across RBAC, fine-grained admin permissions v1, and v2:

* The `view-clients` and `manage-clients` admin roles grant visibility to all clients.
* Fine-grained admin permissions v1 grant client visibility through the `view`, `configure`, or `manage` permission.
* Fine-grained admin permissions v2 keep the Clients `view` and `manage` scopes independent. When access is granted only through fine-grained permissions, `manage` alone does not grant visibility.

Counts for visible clients continue to include all their sessions, independently of the caller's permission to view the associated users.

=== SAML back-channel SLO via SessionIndex requires client signature
// https://github.com/keycloak/keycloak/issues/53535

Back-channel SAML single logout that identifies the session with `SessionIndex` (no browser cookie) now requires the initiating client to have *Client signature required* (`saml.client.signature`) enabled.
Without a verified signature, the `Issuer` field is not authenticated and could be forged to terminate another client's session.

Browser-based (front-channel) logout that carries the user's SSO cookie is unchanged and still works for clients that do not require signatures.

If a SAML client uses back-channel SLO with `SessionIndex` and has *Client signature required* set to *OFF*, either:

* Enable *Client signature required* and configure the client's signing certificate, then sign `LogoutRequest` messages, or
* Prefer front-channel logout so the browser cookie authenticates the request.

Newly created SAML clients already default to requiring client signatures. Deployments that import realm JSON may still have unsigned clients and are the primary group affected by this change.

=== Email verification before domain-based organization membership

Automatic membership through a linked identity provider now requires a verified email address when the organization has configured domains.
Previously, a matching email domain could grant membership before email verification. The first broker login flow now verifies an unverified address before granting membership, even when the realm's *Verify email* setting is disabled.
If email delivery is unavailable, users whose addresses require local verification cannot complete onboarding.

Before upgrading:

. Configure and test the realm's outgoing SMTP settings under *Realm settings* -> *Email* so users can receive verification links. Test first login with an unverified address matching an organization domain.
. Review each linked identity provider's *Trust Email* setting. Enable it only if the provider establishes ownership of the email addresses it supplies; do not enable it just to bypass verification.

An OpenID Connect provider returning `email_verified=false` still requires local verification even with *Trust Email* enabled. An address changed during first-login profile review also requires verification, so email delivery must work for these cases.

Existing memberships are not removed or revalidated. Review memberships previously granted from unverified addresses and remove any that should not have been granted.
Organizations without domains and invitation-based membership are unaffected. The verification requirement applies to both managed and unmanaged automatic membership, including through shared identity providers.

If verification is completed in another browser or the original authentication session is lost, users must sign in through the same identity provider account again and follow the account-linking prompts.
Verification of an unchanged address is preserved for the next onboarding retry within the configured email-verification lifespan, including with `FORCE` synchronization. If that temporary state expires or is lost, verification may be requested again; a different unverified address still requires verification.
Identity provider mappers using `IMPORT` are not replayed on this retry. Check any attributes, roles, or group assignments that onboarding relies on those mappers to supply.

Custom identity providers that synchronize email outside `AbstractIdentityProvider` should implement `UserAuthenticationIdentityProvider.updateBrokeredEmail` to expose their email verification policy before organization membership is granted.

== Notable changes

Notable changes may include internal behavior changes that prevent common misconfigurations, bugs that are fixed, or changes to simplify running {project_name}.
It also lists significant changes to internal APIs.

=== Custom truststore in `kcadm` and `kcreg` now rejects self-signed certificates not present in the truststore

When `kcadm` or `kcreg` is configured with a custom truststore (via `--truststore` or `config truststore`), a self-signed server certificate is now only accepted if it has been explicitly imported into that truststore. Previously, any self-signed certificate was accepted regardless of the truststore contents.

If you use a custom truststore and connect to a {project_name} server with a self-signed certificate, ensure that certificate is imported into your truststore:

[source,bash]
----
keytool -exportcert -alias <server-alias> -keystore <server-keystore.p12> \
  -storepass <password> -file server.crt -rfc

keytool -importcert -alias <server-alias> -file server.crt \
  -keystore <truststore.p12> -storepass <password> -noprompt
----

Deployments using CA-signed certificates or a truststore that already contains the server certificate are not affected.

=== In-flight browser logouts may restart during a rolling upgrade (CVE-2026-107124)
// https://github.com/keycloak/keycloak-private/issues/1294

A new `LOGOUT_USER_SESSION_ID` auth note is now stored on every logout authentication session.
This note is used to ensure that a logout session is only reused for the same user session, preventing session reuse attacks.

The root authentication session of a browser logout now has a random id instead of the id of the user session.
That id is stored in a new `LOGOUT_ROOT_SESSION_ID` user session note, so that the logout session can be found again when the browser returns from an identity provider without the `AUTH_SESSION_ID` cookie, for example after a cross-site POST.

During a rolling upgrade, logout authentication sessions created by older nodes will not carry these notes.
If a browser is mid-logout on an older node and the request is subsequently handled by an upgraded node, the reuse guard will not match and the logout flow will restart from the beginning.
The same applies if a logout started on an upgraded node is continued on an older node.
If the browser also returns from the identity provider without the `AUTH_SESSION_ID` cookie, the values saved at the start of the logout, such as `post_logout_redirect_uri` and `state`, are not found, and the user is not redirected back to the client.
The logout will still complete correctly; the only observable effect is that the browser goes through the logout redirect sequence a second time or is not redirected back to the client.
No user action is required.

=== The `admin-permissions` client is treated as an internal client
// https://github.com/keycloak/keycloak/issues/51630

When fine-grained admin permissions V2 are enabled on a realm, the `admin-permissions` client holds the whole authorization model of that realm.
This client is now treated as an internal client, the same way the `realm-management` client already is, so it can no longer be managed through the Admin REST API.
Previously, an administrator with a *manage* permission on clients could update it, including changing its `clientId`, even though the `access.manage` field returned for the client was already `false`.

After upgrading, requests that update the `admin-permissions` client are rejected with a 403 status.
Requests that delete it are also rejected with a 403 status, where previously they were rejected with a 400 status.
Configuring the permissions and the policies of the realm is not affected, as it requires the `manage-realm` role rather than a permission on the client.

=== User storage periodic sync runs at the configured period again

Periodic full and changed-users synchronization for a user storage provider now starts every `fullSyncPeriod` or `changedSyncPeriod` seconds, as documented.
A regression caused a sync to run only on every other scheduled tick, so the effective interval was about twice the configured period, whenever a single sync took longer than roughly one second.
The provider's last-sync time is now recorded when a sync starts rather than when it finishes, so the schedule no longer drifts by the sync duration.

If you previously lowered `fullSyncPeriod` or `changedSyncPeriod` to compensate for the doubled interval, review those values.

=== Parsing SAML 1.1 requests disabled by default

SAML protocol version 1.1 has never been supported by {project_name}. However, parsers for the SAML 1.1 version have been enabled by mistake. From this release on they are disabled by default and can be re-enabled using `--spi-login-protocol--saml--enable-saml11=true` option when starting the server.

WARNING: If you are using obsolete SAML 1.1 protocol you should stop using it as soon as possible.

For information see the `login-protocol` provider configuration in the link:{allproviderconfigguide_link}[{allproviderconfigguide_name}].
