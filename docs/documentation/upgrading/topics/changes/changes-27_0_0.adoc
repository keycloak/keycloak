// ------------------------ Breaking changes ------------------------  //
== Breaking changes

Breaking changes are identified as those that might require changes for existing users to their configurations or applications.
In minor or patch releases, {project_name} will only introduce breaking changes to fix bugs.

=== Admin client `organizations.findOne` no longer rejects when the organization does not exist
// https://github.com/keycloak/keycloak/pull/51717

The `organizations.findOne` method in the `@keycloak/keycloak-admin-client` package now resolves to `undefined` when the organization does not exist, instead of rejecting with a 404 error.
Its declared return type changes from `OrganizationRepresentation` to `OrganizationRepresentation | undefined`.

This aligns the method with the equivalent lookups on other resources, such as `groups.findOne`, `roles.findOneById`, and `clients.findOne`, which already resolve to `undefined` for a missing entity.

After upgrading, code that relies on a rejected promise to detect a missing organization no longer takes that path.
TypeScript users see a compilation error wherever the result is used without a check.
Plain JavaScript users receive `undefined` instead of an error, and may only observe the change at a later point in their code.

Replace any handling that catches a 404 from this method with a check for `undefined`:

[source,typescript]
----
const organization = await adminClient.organizations.findOne({ id });

if (!organization) {
  // handle the missing organization
}
----

=== Mandatory signature validation for OIDC identity provider backchannel logout tokens

{project_name} now always validates the signature of backchannel logout tokens received from external OIDC identity providers, regardless of the `Validate Signatures` setting on the identity provider configuration. This change addresses CVE-2026-18569, where an unauthenticated attacker could forge unsigned logout tokens (using `alg=none`) to force-logout targeted users when signature validation was disabled.

The OIDC Back-Channel Logout 1.0 specification mandates that logout tokens MUST be signed and that `alg=none` is explicitly prohibited. {project_name} now enforces this requirement.

Other token types (ID tokens, access tokens) continue to respect the `Validate Signatures` setting as before.

If your OIDC identity provider has `Validate Signatures` set to *OFF* and uses backchannel logout, you must configure the identity provider's public key so that {project_name} can validate logout token signatures. Either:

* Set `Use JWKS URL` to *ON* and configure the `JWKS URL` pointing to the external IDP's JWKS endpoint, or
* Provide the IDP's public key directly via the `Validating Public Key` field and, if needed, its key ID via the `Validating Public Key Id` field.

=== Identity provider client secret must be re-entered when changing its destination (CVE-2026-15943)

When reading an OpenID Connect, OAuth 2.0, or social identity provider through the Admin REST API, the `clientSecret` is returned masked as `**********`.
Previously, an update that sent this masked value back always kept the stored secret, even if the request also changed where that secret is sent.
A user with the `manage-identity-providers` role could therefore point the identity provider at an attacker-controlled token endpoint and have {project_name} send the real client secret there.

Starting with this release, the stored secret is kept only when the fields that determine where and how it is sent are unchanged: `clientId`, `clientAuthMethod`, `tokenUrl`, `tokenIntrospectionUrl`, and `baseUrl` (GitHub and OpenShift), as well as `tenantId` (Microsoft) and `sandbox` (PayPal).
If any of these change while the request still contains the masked value, the update is rejected with HTTP `400 Bad Request` and the identity provider is left unchanged.
To apply such a change, include the actual `clientSecret` in the request.
The Admin Console clears the *Client Secret* field automatically when one of these fields is edited so that you can enter it again.

The `providerId` of an existing identity provider can no longer be changed through an update request; sending a different value is rejected with HTTP `400 Bad Request`.

Scripts and tools that read an identity provider, modify one of the fields above, and write it back (for example, `kcadm.sh update identity-provider/instances/<alias> -s config.tokenUrl=...`) must now also pass the client secret (`-s config.clientSecret=...`).
Updates that change other settings, or that use a `${vault.<key>}` expression as the secret, are not affected.

Custom identity providers whose secret is sent to a destination derived from provider-specific configuration can take part in this check by overriding `IdentityProviderModel#canReuseMaskedClientSecret` in the model returned by `IdentityProviderFactory#createConfig()`.
Providers extending `OAuth2IdentityProviderConfig` can instead override `getClientSecretDestinationConfigKeys()` and `isClientSecretDestinationChanged()`.

== Notable changes

=== Scope mapping listings filter roles by visibility
// https://github.com/keycloak/keycloak/issues/53480

The Admin REST API endpoints for reading the scope mappings of a client or a client scope (`GET /admin/realms/\{realm}/clients/\{id}/scope-mappings` and `GET /admin/realms/\{realm}/client-scopes/\{id}/scope-mappings`, including their `realm`, `realm/composite`, `clients/\{client}` and `clients/\{client}/composite` sub-resources) now filter out roles that the caller is allowed neither to view nor to map to users or to client scopes.
Previously, any caller with permission to view the client or the client scope could see all the roles in its scope, including realm roles without the `view-realm` role and client roles without a *view* permission on the client they belong to.
After upgrading, callers may see fewer results from these endpoints if the scope contains roles that they are allowed neither to view nor to map.
Roles that the caller is allowed only to map to client scopes are returned without their attributes, even when `briefRepresentation=false` is requested.
For example, an administrator with the `view-clients` role but without the `view-realm` role no longer sees the realm roles in the scope of a client, unless they are allowed to map these roles to users, for example through the `manage-users` role, or to client scopes.
With fine-grained admin permissions V2, an administrator with a *view* permission on a client no longer sees the roles of other clients in its scope, unless they are also allowed to view these other clients, or to map their roles to users (*map-role* on the role or *map-roles* on the client) or to client scopes (*map-role-client-scope* on the role or *map-roles-client-scope* on the client).
In the Admin Console, these roles are no longer listed in the *Scope* tab of client scopes and of dedicated client scopes.

=== Admin Console uses the Admin API to list and assign roles
// https://github.com/keycloak/keycloak/issues/53747

The Admin Console previously relied on internal `ui-ext` endpoints to search the client roles that can be assigned to users, groups, clients, client scopes, and composite roles, to list effective roles, and to remove role mappings.
Those endpoints applied coarser permission checks than the Admin API.
For example, an administrator with the `view-clients` role could see the roles of a client in the Admin Console, but could not select them when creating a role-based authorization policy unless they also had the `manage-users` role.

The Admin Console now uses the Admin API for these operations, so that the same permissions apply regardless of whether roles are managed from the Admin Console or through the Admin API.
To support this, the following endpoints have been added to the Admin API:

* `GET /admin/realms/\{realm}/clients/roles` lists the client roles of all clients of the realm, grouped by client.
Only the roles the caller is allowed to view are returned, so the `view-clients` role is enough to pick client roles when, for example, creating a role-based authorization policy.
* `GET /admin/realms/\{realm}/users/\{id}/role-mappings/composite` and `GET /admin/realms/\{realm}/groups/\{id}/role-mappings/composite` return the effective role mappings across the realm and all clients, that is, with composite roles expanded and, for users, including the roles inherited from groups.
* `GET /admin/realms/\{realm}/users/\{id}/role-mappings/inherited` and `GET /admin/realms/\{realm}/groups/\{id}/role-mappings/inherited` return only the roles obtained through composite roles and, for users, through group membership, so that a role that is both mapped directly and inherited can be told apart.
* `GET /admin/realms/\{realm}/users/\{id}/role-mappings/available` and `GET /admin/realms/\{realm}/groups/\{id}/role-mappings/available` return the roles that are not yet mapped and that the caller is allowed to map.
* `GET /admin/realms/\{realm}/clients/\{id}/scope-mappings/composite`, `GET /admin/realms/\{realm}/client-scopes/\{id}/scope-mappings/composite`, and the corresponding `/inherited` and `/available` endpoints provide the same for scope mappings.
* `GET /admin/realms/\{realm}/roles-by-id/\{id}/composites/composite` returns the effective children of a composite role, `GET /admin/realms/\{realm}/roles-by-id/\{id}/composites/inherited` the children obtained through its composite children, and `GET /admin/realms/\{realm}/roles-by-id/\{id}/composites/available` the roles that can still be added as children by the caller.

The `/composite`, `/inherited`, and `/available` endpoints return a `MappingsRepresentation` with the roles grouped by realm and client, while `GET /admin/realms/\{realm}/clients/roles` returns a list of `ClientMappingsRepresentation`.
Client roles are paginated with the `first` and `max` parameters and filtered with the `search` parameter, which matches the role name or the client ID.
Realm roles returned by the `/available` endpoints are not paginated.

The Java and JavaScript admin clients expose the new endpoints.

The `GET /admin/realms/\{realm}/clients/\{id}/scope-mappings` and `GET /admin/realms/\{realm}/client-scopes/\{id}/scope-mappings` endpoints, previously deprecated, are now used by the Admin Console and are no longer deprecated.

The following internal `ui-ext` endpoints have been removed:

* `GET /admin/realms/\{realm}/ui-ext/available-roles/\{type}/\{id}`
* `GET /admin/realms/\{realm}/ui-ext/effective-roles/\{type}/\{id}`
* `GET /admin/realms/\{realm}/ui-ext/effective-roles-all/\{type}/\{id}`
* `GET /admin/realms/\{realm}/ui-ext/role-mappings/roles/\{id}`
* `POST /admin/realms/\{realm}/ui-ext/role-mapping-delete/\{type}/\{id}`

These endpoints were not part of the public Admin API and were only intended for the Admin Console.
If you have custom scripts that call them, use the Admin API endpoints listed above instead.

As a consequence, removing role mappings from a group in the Admin Console now requires the `manage` permission on the group when fine-grained admin permissions are enabled, consistent with the Admin API, instead of the `manage-membership` permission.

=== Organization Redirect URL now validated against the account client

The Redirect URL configured on an organization is now validated against the valid redirect URIs of the `account` client. If the URL is not listed in the client's allowed redirect URIs, the user is redirected to the account console instead. When a custom client is specified in the invitation, the organization's Redirect URL is ignored and the user is redirected to the custom client's base URL.

Previously, the Redirect URL was used without validation, which could allow an open redirect. After upgrading, if your organization has a custom Redirect URL pointing to your application, you must add that URL to the `account` client's *Valid Redirect URIs*. Otherwise, the redirect will silently fall back to the account console. This does not apply to invitations sent with a custom client, which always use the client's own base URL.

The `invite-existing-user` endpoint now also accepts an optional `client_id` query parameter, the same way `invite-user` already does. If omitted, both endpoints default to the `account` client.

// ------------------------ Deprecated features ------------------------ //
== Deprecated features

The following sections provide details on deprecated features.

=== Organization Redirect URL

The organization Redirect URL field is now deprecated and will be removed in a future release. When sending invitations, prefer selecting a client to control where users are redirected. Create a client with its base URL set to your desired redirect destination and pass its `client_id` when creating invitations.

=== Organization invitation endpoints without `client_id`

The `invite-user` and `invite-existing-user` admin client overloads that do not accept a `client_id` parameter are now deprecated. Use the overloads that accept an explicit `client_id` instead. When omitted, the endpoints default to the `account` client, but callers should migrate to always specify a client.
