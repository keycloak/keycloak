== Breaking changes

Breaking changes are identified as those that might require changes for existing users to their configurations or applications.
In minor or patch releases, {project_name} will only introduce breaking changes to fix bugs.

=== Validation of client URI fields
// https://github.com/keycloak/keycloak/issues/54046

Client URI validation and client policies now share a catalog of URI fields. Existing policy configuration keys, selected field names, regular expressions, and wildcard options retain their meaning.
The following additional checks can reject previously accepted client configurations:

* With *Client URIs Must Match* enabled, the *Trusted Hosts* client registration policy checks all supplied URI fields on creation and update, including post-logout redirects, logout endpoints, web origins, JWKS and request URIs, CIBA notification endpoints, logo, policy, terms of service, sector identifier attributes, and SAML endpoints and metadata URLs. Add any legitimate external hosts to the trusted-host list before updating these clients. Post-logout `*` is rejected because it permits redirects to any host. Explicit URLs accompanying `+` or `-` are also checked.
* The *Secure Client URIs* executor additionally requires HTTPS without wildcards for sector identifier attributes and SAML endpoints and metadata URLs, regardless of the configured client protocol.
* The *SAML Secure Client URIs* executor checks all catalog fields on SAML clients, including stored metadata during login and logout. Replace HTTP URLs with HTTPS URLs or remove unused values before upgrading with this executor enabled or enabling it for the first time. Stored `*` or `null` web origins and embedded `data:` logos also fail its HTTPS check, even if they are unused by SAML. The `allow-wildcard-redirects` option still applies only to redirect URIs.
* General client validation additionally checks web origins, sector identifier attributes, and supplied SAML URL attributes even on clients using another protocol. Malformed or disallowed values must be corrected before saving or importing those clients.

These changes close gaps where a URL could evade a policy simply because it was stored in a different client field. A policy configuration migration is not required, but continuing to accept those previously unchecked URLs would leave the gaps open.
Relative URLs, embedded `data:` logos, and web origin markers `+`, `*`, and `null` retain their meaning in general validation and Trusted Hosts. The HTTPS executors still enforce their own scheme restrictions.
General validation also preserves the legacy web origin literals `${authAdminUrl}`, `${authBaseUrl}`, and `file://`. These values remain subject to the host, HTTPS, and pattern restrictions of any enabled client policies.
Trusted Hosts resolves relative logo URLs against the {project_name} frontend URL and checks that host against its allowlist. The client's root URL does not determine where the browser loads a logo.
The pattern executor continues to match literal configured values, including markers and relative URLs, and respects an explicit field selection. Sector identifier URLs in pairwise protocol mappers remain subject to their separate validation.

=== CIBA requires client authentication (CVE-2026-109082)
// https://github.com/keycloak/keycloak/issues/53937

The Client Initiated Backchannel Authentication (CIBA) grant is now rejected for public clients, as required by the https://openid.net/specs/openid-client-initiated-backchannel-authentication-core-1_0.html#rfc.section.7.1[CIBA specification], which mandates client authentication on both the backchannel authentication endpoint and the token endpoint.
Previously, a public client with the CIBA grant enabled could complete the flow without authenticating and obtain tokens for the approving user.


=== Realm-level default client scopes require `manage-realm`
// https://github.com/keycloak/keycloak/issues/50588

Changing the realm-level default and optional client scopes through the Admin REST API endpoints `default-default-client-scopes/{clientScopeId}` and `default-optional-client-scopes/{clientScopeId}` now requires the `manage-realm` role.
Previously `manage-clients` was sufficient, even though these lists determine which client scopes every newly created client in the realm receives.
Administrators who hold only `manage-clients` can still create, update, and delete individual client scopes, and can still read the realm-level lists; they can no longer change which of them are realm defaults.
If you have automation that manages realm default client scopes with a `manage-clients` account, grant it `manage-realm` or run it with an account that already has it.

=== Session note mappers no longer expose internal credentials or user models

When a user authenticates through an external identity provider, {project_name} stores the tokens issued by that provider as notes on the user session.
The supported way to retrieve them is the broker token endpoint; its authorization requirements depend on the enabled Identity Brokering API version.
Previously, the *User Session Note* mapper copied any session note into a token claim without checking what the note held.
An administrator who only held the `manage` permission on a single client could therefore configure a mapper for `FEDERATED_ACCESS_TOKEN` and receive the upstream token of every user who logged in to that client, bypassing the broker token endpoint's authorization checks entirely.
The same applied to the SAML *User Session Note* mapper, which copied the note into a SAML attribute.

Both mappers now refuse to read the session notes that hold identity provider tokens: `FEDERATED_ACCESS_TOKEN`, `FEDERATED_REFRESH_TOKEN`, `FEDERATED_TOKEN_EXPIRATION`, and `FEDERATED_ID_TOKEN`, together with the per-provider forms such as `FEDERATED_ACCESS_TOKEN:my-idp`.
They also refuse to read `keycloak.userModel`, which holds the serialized user model when the experimental transient-users feature is used.
This internal representation includes user attributes, role and group identifiers, and consent data, and must not be copied wholesale to application tokens.
The documented Kerberos GSS credential delegation mapper and ordinary application session notes remain supported.

Creating or updating a client with such a mapper is rejected with a `400 Bad Request`, and so is importing a realm that contains one.
A mapper that already exists, because it was configured before upgrading, is retained but no longer produces a claim or an attribute, and {project_name} logs a warning naming the mapper and the client.

Existing deployments continue to start because the mappers are read from the database rather than imported, but a client with such a mapper cannot be updated until the mapper is removed.
If you provision realms from an exported JSON file, remove the mapper from the file before importing it again.

After upgrading, if any of your applications read an identity provider token from a token claim or a SAML attribute, change them to call the broker token endpoint; its authorization requirements depend on the enabled Identity Brokering API version.
For more details, see the link:{adminguide_link}#retrieving-external-idp-tokens[Retrieving external IDP tokens] section of the {adminguide_name}.

=== Protocol mappers are validated when a client or a client scope is written as a whole

Previously, a protocol mapper was validated only when it was written through the mapper endpoints of the Admin REST API.
A mapper sent as part of a client or a client scope, such as during client registration, partial import, or realm import, was stored without being validated, so a mapper rejected by one path was accepted by another.

Starting with this release, every protocol mapper of a client is validated whenever the client is created or updated as a whole, using the same rules as the mapper endpoints. Client scope creation and realm import also validate their protocol mappers.
A mapper with an invalid configuration is now rejected with a `400 Bad Request`, where it was previously stored and silently ignored, or failed later at runtime.

The validation covers all the mappers of the client, not only the one being changed.
A client that carries a mapper stored before the upgrade whose configuration is no longer valid cannot be updated at all, even for an unrelated field, until that mapper is corrected or removed.
Updating an existing client scope does not revalidate its stored mappers.

Existing deployments continue to start, because mappers that are read from the database at startup are not validated.
If you provision realms from an exported JSON file, import the file once after upgrading to find out whether it contains a mapper that is now rejected.

=== SCIM listings respect per-resource view permissions (CVE-2026-116470)
// https://github.com/keycloak/keycloak/issues/54340

Listing and searching resources through the SCIM API now returns only the resources the caller is allowed to view.
Previously, the `query-users` and `query-groups` roles were checked when entering `GET /realms/\{realm}/scim/v2/Users`, `GET /realms/\{realm}/scim/v2/Groups`, and their `.search` counterparts, but the resources those endpoints matched were returned in full without a per-resource view check.
A service account holding only `query-users` could therefore read every user in the realm, including email addresses, names, and custom attributes, which the Admin REST API would not have disclosed to it.

The query roles now behave as they do in the Admin REST API: they grant access to the listing and search endpoints, not read access to the resources those endpoints match.
After upgrading, a client holding only `query-users` or `query-groups` receives an empty `Resources` array.
Grant `view-users` in addition, or configure a fine-grained `view` permission on the users and groups the client is allowed to see.
When fine-grained admin permissions v2 are enabled for the realm, listings were already narrowed to the permitted resources and are unaffected.

With fine-grained admin permissions v2, the listing and the count are restricted by the same authorization filter in the database query, so `totalResults` stays exact.
With the deprecated fine-grained admin permissions v1, a caller can be allowed to view some resources but not others, so `totalResults` counts the resources matching the query, before the per-resource view check is applied, and should be treated as an upper bound; a page can also be shorter than the requested `count`, or even empty, while later pages still contain resources the caller is allowed to see, so neither a short page nor an empty page means that no further resources exist, and clients should keep incrementing `startIndex` by `count` until `startIndex` exceeds `totalResults`.
Without any fine-grained admin permissions, the per-resource view check evaluates the same way for every resource of a given type, so access is all-or-nothing: a client holding only a query role and no realm-wide view role gets a `totalResults` of `0`, consistently across every page, rather than the unfiltered database count.

== Notable changes

Notable changes may include internal behavior changes that prevent common misconfigurations, bugs that are fixed, or changes to simplify running {project_name}.
It also lists significant changes to internal APIs.

=== Existing AES key sizes are recorded during migration

When upgrading, existing `aes-generated` key providers without an explicit `secretSize` are updated to record the size of their stored key, including databases already running 26.8.x.
This ensures the Admin Console displays the actual key size and saving a provider without changes preserves its key and key ID.
Providers with an explicitly configured size are preserved.

=== `secure-redirect-uris-enforcer` now always validates post-logout redirect URIs
// https://github.com/keycloak/keycloak/issues/50982

The `secure-redirect-uris-enforcer` client policy executor previously skipped post-logout redirect URI validation when both standard flow and implicit flow were disabled on a client.
This allowed a delegated client manager to retain an HTTP (insecure) post-logout redirect URI by temporarily disabling both flows, then re-enabling them via a partial update that omitted the `post.logout.redirect.uris` attribute.

Post-logout redirect URIs are now always validated on every CREATE and UPDATE event, regardless of whether redirect-based flows are enabled.

Additionally, a partial update that omits the `post.logout.redirect.uris` attribute now causes the executor to re-validate the URIs already stored in the model, rather than silently accepting the update.

*Impact on existing clients*

The following clients may be rejected by CREATE or UPDATE operations after upgrading:

* Clients with both standard flow and implicit flow disabled that have redirect URIs
that violate the executor's configured rules and either no explicit
`post.logout.redirect.uris` attribute or the `{plus}` placeholder.
The absent or `{plus}` attribute inherits the client's redirect URIs, which are
now validated as post-logout redirect URIs.

* Clients that have an explicit `post.logout.redirect.uris` value stored in their
attributes that violates the executor's configured rules — whether set before
the policy was active or retained through the partial-update bypass this fix
addresses. Any partial admin update to such a client, including routine changes
like renaming, now triggers revalidation of the stored post-logout URIs.

Before upgrading, audit clients matched by the `secure-redirect-uris-enforcer`
policy against all of its configured URI rules. To disable post-logout redirects
on an affected client, set `post.logout.redirect.uris` to `-`; otherwise, update
its post-logout redirect URIs to satisfy those rules. Setting `-` also works
after upgrading, so an affected client can still be remediated.

=== Organization Redirect URL now validated against the account client

The Redirect URL configured on an organization is now validated against the valid redirect URIs of the `account` client. If the URL is not listed in the client's allowed redirect URIs, the user is redirected to the account console instead. When a custom client is specified in the invitation, the organization's Redirect URL is ignored and the user is redirected to the custom client's base URL.

Previously, the Redirect URL was used without validation, which could allow an open redirect. After upgrading, if your organization has a custom Redirect URL pointing to your application, you must add that URL to the `account` client's *Valid Redirect URIs*. Otherwise, the redirect will silently fall back to the account console. This does not apply to invitations sent with a custom client, which always use the client's own base URL.

The `invite-existing-user` endpoint now also accepts an optional `client_id` query parameter, the same way `invite-user` already does. If omitted, both endpoints default to the `account` client.

=== OIDC identity provider now respects `email_verified=false` from the ID token when Trust Email is enabled
// https://github.com/keycloak/keycloak/issues/54245

When brokering through an OpenID Connect identity provider with *Trust Email* enabled, {project_name} now correctly honors an `email_verified=false` claim in the ID token, even when the UserInfo endpoint does not include an `email_verified` field.

Previously, if a provider such as GitLab supplied `email_verified=false` in the ID token but omitted the claim from UserInfo, {project_name} ignored the token value and fell back to the `trustEmail` setting, marking the email as verified despite the IdP explicitly stating otherwise.

After upgrading, the following behavior applies when *Trust Email* is enabled:

* If UserInfo includes `email_verified`, that value is used and the ID token value is ignored.
* If UserInfo provides an email but omits `email_verified`, the ID token's `email_verified` value is used, provided the two emails match.
* If UserInfo returns a different email than the ID token, the ID token's `email_verified` claim is discarded because it does not apply to the email that was actually selected. {project_name} falls back to the default trust-email behavior for that email.
* If a custom provider stores the validated ID token under `VALIDATED_ID_TOKEN` in the brokered identity context but does not explicitly set an `EMAIL_VERIFIED` context entry, {project_name} reads `email_verified` directly from the token as a fallback, again only when the token and context emails match.

The change affects existing users under FORCE synchronization mode. When UserInfo provides the user's email but omits `email_verified`, {project_name} now applies the ID token's `email_verified` value, whether `true` or `false`, on every login, even if the user's email address has not changed since the last login.
For example, if an administrator marked the user's email as not verified, a later login whose ID token carries `email_verified=true` sets the flag back to `true`. Conversely, a token carrying `email_verified=false` sets it to `false` even if the administrator marked the email as verified.
Previously, the flag was left unchanged for existing users with an unchanged address in this situation.
If this behavior is not desired, set *Trust Email* to *OFF* for that identity provider. {project_name} then leaves the flag unchanged for existing users whose email address has not changed, and sets it to `false` for new users until the email is verified locally.

// ------------------------ Deprecated features ------------------------ //
== Deprecated features

The following sections provide details on deprecated features.

=== Organization Redirect URL

The organization Redirect URL field is now deprecated and will be removed in a future release. When sending invitations, prefer selecting a client to control where users are redirected. Create a client with its base URL set to your desired redirect destination and pass its `client_id` when creating invitations.

=== Organization invitation endpoints without `client_id`

The `invite-user` and `invite-existing-user` admin client overloads that do not accept a `client_id` parameter are now deprecated. Use the overloads that accept an explicit `client_id` instead. When omitted, the endpoints default to the `account` client, but callers should migrate to always specify a client.

=== Atomic credential update for custom credential stores
// https://github.com/keycloak/keycloak/issues/55028

The new methods `SubjectCredentialManager.updateStoredCredential(oldCred, newCred)`, `UserCredentialStore.updateCredential(realm, user, oldCred, newCred)` and `UserFederatedUserCredentialStore.updateCredential(realm, userId, oldCred, newCred)` replace a credential only if the stored credential still has the content of `oldCred`, and return `false` otherwise.
{project_name} uses them to re-hash a password after a login, so that a password or label that was changed in the meantime is not overwritten.

Custom implementations of these interfaces should override the new methods, and perform the comparison and the update atomically, for example by locking the stored credential.
The default implementations exist only for backwards compatibility.
They check and update in two separate steps, so a concurrent change can still be lost.
The default implementations will be removed in a future release, at which point custom implementations that do not provide the methods will no longer compile.
