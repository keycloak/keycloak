== Breaking changes

Breaking changes are identified as those that might require changes for existing users to their configurations or applications.
In minor or patch releases, {project_name} will only introduce breaking changes to fix bugs.

=== Client secret no longer returned for view-only client permissions
// https://github.com/keycloak/keycloak/issues/49220

The Admin REST API endpoints for retrieving client representations (`GET /admin/realms/\{realm}/clients` and `GET /admin/realms/\{realm}/clients/\{id}`) no longer include the client secret in the response when the caller only has `view-clients` permission.
To view the client secret, the caller must have `manage-clients` permission.

Previously, any caller with the `view-clients` role could read client secrets from the API response, which posed a security risk as it allowed read-only administrators to access sensitive credentials.
After upgrading, callers with only `view-clients` permission will see a masked placeholder (`**********`) instead of the actual secret value.

If you have delegated administrators or automation that reads client secrets using the `view-clients` role, ensure they are granted the `manage-clients` realm admin role or equivalent `manage` permission on the Clients resource type.

=== `initiating_idp` logout parameter ignored by default
// https://github.com/keycloak/keycloak/issues/51243

The `initiating_idp` query parameter on the OIDC RP-initiated logout endpoint is now ignored by default.
This parameter suppressed the logout at the upstream identity provider for the referenced broker.

After upgrading, {project_name} always performs the upstream identity provider logout during a browser logout, regardless of the `initiating_idp` parameter.
To handle logout initiated by an upstream identity provider, rely on the standard OIDC link:https://openid.net/specs/openid-connect-backchannel-1_0.html[back-channel] or link:https://openid.net/specs/openid-connect-frontchannel-1_0.html[front-channel] logout mechanisms instead.

To temporarily restore the previous behavior, enable the `allow-initiating-idp-logout-param` server option for the OpenID Connect provider.
This option is deprecated and will be removed in a future release.

=== X509 user authentication requires CA Subject DN
// https://github.com/keycloak/keycloak/issues/51850

Following the changes made to the X509 client authenticator, in this release the user counterparts also require the **Certificate Authority subject DN** option.
The new configuration attribute is multi-valued and identifies the trusted anchor CA (or CAs) for user certificates.
The new option is now compulsory in the admin console.
Additionally, the option **Revalidate Client Certificate** should always be enabled to get the root certificate for the chain and check its subject DN, so it is now deprecated and no longer presented in the console.
Previous configurations still work to maintain backwards compatibility, but the new behavior will be enforced in the next major version.

Note that {project_name}'s trust store (or mTLS store) is shared across all realms.
The new configuration allows specifying the correct CAs for user certificates and avoids interference with other unrelated CAs.

Revalidating certificates can be problematic in certain installations (for example if a proxy is configured for TLS termination and the certificates are passed to {project_name} using headers).
The trust-store or mTLS store in {project_name} should always be configured correctly to validate the client certificate chain.
Please see link:https://www.keycloak.org/server/reverseproxy[Using a reverse proxy] and link:https://www.keycloak.org/server/mutual-tls[Configuring trusted certificates for mTLS], for more information if you are using a TLS termination proxy and X509 client authentication.

=== Disabled clients are no longer added to the token audience

A disabled or removed client is never added to the `aud` claim of a token, and its client roles are not present in the `resource_access` claim.
Tokens are still issued, only without that client, so logins and refreshes keep succeeding.
This change addresses CVE-2026-93999.

For more details, see link:{adminguide_link}#_audience_disabled_clients[Disabled clients and the audience] in the {adminguide_name}.

=== Resource URI matching in Authorization Services normalizes matrix parameters, dot segments, percent-encoding, and query/fragment components

When matching an incoming request URI against a resource URI configured in Authorization Services (the policy enforcer and the UMA permission endpoint), the URI is now normalized before comparison:

* Matrix parameters (for example `+;jsessionid=...+`), including percent-encoded (`+%3B+`), are stripped.
* Dot segments (for example `+/foo/../admin+`, `+/./admin+`), including percent-encoded (`+%2E%2E+`, `+%2e.+`), are resolved.
* Percent-encoded slashes (`+%2F+`) are decoded, and any duplicate slashes this produces are collapsed.
* A trailing slash is stripped.
* The query string and fragment are dropped before matching, so a resource configured for `+/api/admin+` also matches, for example, `+/api/admin?foo=bar+` and `+/api/admin#section+`.

This prevents a mutated form of a protected resource's URI from evading its configured policy and falling through to a more permissive resource, such as a catch-all `+/*+` resource.

Resources configured with a full absolute URI (a scheme and authority, for example `+https://my.domain/api/admin+`) are unaffected beyond their path component — the scheme and authority are preserved, and only the path is normalized.

If your Authorization Services configuration relies on distinguishing resources by matrix parameters, dot segments, trailing slashes, or query string/fragment content in the resource URI, review your resource and policy configuration, since these are now treated as equivalent to their normalized form.

== Notable changes

=== Secrets referenced by OIDC Client CRs now require a label
// https://github.com/keycloak/keycloak/issues/52320

Kubernetes Secrets referenced via `spec.client.auth.secretRef` in a `KeycloakOIDCClient` CR must now carry the label `operator.keycloak.org/kind: KeycloakOIDCClient`.
Without this label the operator treats the Secret as missing and reports a `HasErrors` status condition on the CR, even if the Secret exists.

This change prevents arbitrary Secrets in the namespace from being read by the operator.

If you already have Secrets used by OIDC Client CRs, add the required label before upgrading:

[source,bash]
----
kubectl label secret <secret-name> operator.keycloak.org/kind=KeycloakOIDCClient
----

=== `NO_PROXY` entries with leading dots or spaces after commas now parsed correctly
// https://github.com/keycloak/keycloak/issues/52706

`NO_PROXY` entries with a leading dot (for example, `.corp.com`) or whitespace after a comma (for example, `localhost, internal.corp.com`) previously failed to match silently, causing traffic to go through the proxy despite the exclusion rule.
Both patterns are now handled correctly.

If your deployment relied on this broken parsing and routed traffic through the proxy intentionally by using a leading-dot entry as a no-op, that traffic will now bypass the proxy after upgrading.

=== `kcadm` and `kcreg` now enforce owner-only permissions on existing configuration files
// https://github.com/keycloak/keycloak/issues/52681

The `kcadm` and `kcreg` CLI tools now set owner-only file permissions (`0600`) on their configuration files every time credentials are written, not only when the file is first created.
Previously, if a configuration file already existed with broader permissions (for example, `0644`), the tools would store access tokens and other sensitive credentials without restricting the file permissions, which posed a security risk as it allowed other users on the same system to read the stored tokens.

After upgrading, any pre-existing configuration file with group- or world-readable permissions will be automatically restricted to owner-only access the next time `kcadm config credentials` or `kcreg config credentials` is executed.
No manual action is required.

=== Login failures now stored in the database by default
// https://github.com/keycloak/keycloak/issues/52126

Login failure data for brute force detection is now stored in the database by default, instead of only in the embedded Infinispan `loginFailures` cache.
This ensures that temporarily locked-out users remain locked out across cluster restarts, and reduces memory consumption from accumulated login failure entries.

This change is controlled by the new `login-failures` versioned feature.
The previous in-memory behavior (`login-failures:v1`) is deprecated.
To restore it, set `--features=login-failures:v1`.
Note that `login-failures:v1` is incompatible with the `stateless` feature.

Deployments using the `multi-site` or `clusterless` features continue to store login failure data in the external Infinispan cluster, regardless of the `login-failures` feature version.

As a trade-off, users may observe increased database connection usage and higher CPU usage on the database.

The option `spi-brute-force-protector-default-brute-force-detector-allow-concurrent-requests` is deprecated and has no effect with `login-failures:v2`.
Instead, concurrent logins for the same user are executed serially for each node.

=== Stateless feature promoted from preview to supported
// https://github.com/keycloak/keycloak/issues/50871

The `stateless` feature has been promoted from preview to supported.
It is disabled by default and can be enabled with `--features=stateless`.

If you previously relied on `--features=preview` to enable the `stateless` feature, you must now enable it explicitly with `--features=stateless`, as `--features=preview` no longer activates supported features.

=== Clusterless feature will be removed
// https://github.com/keycloak/keycloak/issues/52130

The experimental `clusterless` feature will be removed in a future release.
The `stateless` feature is the successor for running {project_name} without depending on an external Infinispan cluster.
While `clusterless` offloads all session data to an external Infinispan cluster, `stateless` stores session data in the database and uses the embedded Infinispan only as a cache.

If you are using `--features=clusterless`, migrate to `--features=stateless` before upgrading to a future release.

Previously, a user's access token was also accepted.

=== Client session listings filter sessions by user visibility
// https://github.com/keycloak/keycloak/issues/48858

The Admin REST API endpoints for listing client sessions (`GET /admin/realms/\{realm}/clients/\{id}/user-sessions` and `GET /admin/realms/\{realm}/clients/\{id}/offline-sessions`) now filter out sessions belonging to users that the caller does not have permission to view.
Previously, any caller with the `view-clients` role could see all user sessions for a client, potentially exposing user identities to callers without the `view-users` role.
After upgrading, callers without `view-users` permission will see fewer results from these endpoints.

=== Redesigned identity provider buttons on the login page

=== Token introspection `act` claim now uses user ID for `sub`
// https://github.com/keycloak/keycloak/issues/51489

The token introspection endpoint previously set the `act.sub` field to the impersonator's username.
It now uses the impersonator's user ID to be consistent with the `act` claim in JWT access tokens and ID tokens.
The `preferred_username` field has been added to the introspection `act` object for consumers that need the impersonator's username.

If you have resource servers that parse `act.sub` from introspection responses and expect a username, update them to read `act.preferred_username` instead.

=== Group policy matching for bare group names (CVE-2026-19608)
// https://github.com/keycloak/keycloak/issues/51865

Group-based policies in Authorization Services use the groups claim from the token as the first source of truth.
When the claim is not defined or empty, the policy falls back to the user's actual group memberships from the realm.
Bare group names in token claims are now resolved to top-level realm groups only.
Previously, a bare name like `Admins` in a group claim would match any group named `Admins` regardless of its position in the group hierarchy.
This allowed users who are members of one group to satisfy policies targeting a different group with the same name at a different path.

If your deployment uses the Group Membership protocol mapper with *Full group path* disabled and relies on group policies targeting nested groups, enable *Full group path* in the protocol mapper configuration so that tokens include the complete group path (for example, `/Organization/Admins` instead of `Admins`).

Group names that contain slashes (for example, a group named `/Organization/Admins`) are now resolved as top-level group names first, before being treated as paths.
This prevents a group name from being confused with a nested group path.

Group policies that use full group paths in claims are not affected unless a top-level group name is identical to a nested group path.
In that ambiguous case, the top-level group name takes precedence.

=== Token exchange delegation now requires FGAP V2 permissions
// https://github.com/keycloak/keycloak/issues/51481

The experimental token exchange delegation feature no longer uses the `impersonation` role from the `realm-management` client to authorize delegation.
Instead, delegation is controlled exclusively through link:{adminguide_link}#_fine_grained_permissions[Fine-grained admin permissions version 2] (FGAP V2) using the new `delegate` scope on the Users resource type and the `delegate-members` scope on the Groups resource type.

If you were previously using delegation with the `impersonation` role, you need to:

. Enable Admin Permissions (FGAP V2) on your realm.
. Create a User permission with the `delegate` scope and assign a policy targeting the administrators or service accounts that should be allowed to delegate.
Alternatively, create a Group permission with the `delegate-members` scope to grant delegation for members of a specific group.

FGAP V1 does not support delegation permissions.

=== Token exchange delegation scope renamed from `delegation` to `delegation:user`
// https://github.com/keycloak/keycloak/issues/51905

The parameterized client scope used by the experimental token exchange delegation feature has been renamed from `delegation` to `delegation:user` to better reflect that this scope targets delegation to a specific user (administrator).

The full scope format in token requests changes from `delegation:<administrator>` to `delegation:user:<administrator>`.
For example, a scope value that was previously `delegation:admin1` is now `delegation:user:admin1`.

During migration, the `delegation:user` and `delegation:client` client scopes are automatically created in existing realms as *Optional* client scopes.
Delegation also requires configuring a delegation permission through FGAP V2. If you had a `delegation` client scope from a previous version, it can be safely removed after migration.
Update clients and automation to request `delegation:user:<administrator>`.

=== Email is no longer marked as verified by other flows
// https://github.com/keycloak/keycloak/issues/50618

Previously, some flows marked the email of a user as verified even though their purpose was not email verification.
This could make an account registered by a different party than the owner of the email address look trusted.
An email is now marked as verified only when the user completes an email verification.
This changes the behavior of identity provider account linking by email, of admin-initiated action emails that do not include the *Verify Email* action, and of the verifiable credential offer emails of the OID4VCI feature.
The *Trust Email* setting of identity providers and LDAP federation is not affected, as it is an explicit decision of the administrator to trust the email from the external source.

=== Offline session expiration indexes rebuilt with session bucket and coarse refresh columns
// https://github.com/keycloak/keycloak/issues/51900

The `OFFLINE_USER_SESSION` table has a new `LAST_SESSION_REFRESH_COARSE` column and updated indexes `IDX_USER_SESSION_EXPIRATION_CREATED` and `IDX_USER_SESSION_EXPIRATION_LAST_REFRESH`.
On PostgreSQL and Microsoft SQL Server, `IDX_OFFLINE_USS_BY_BROKER_SESSION_ID` is also rebuilt as a filtered index.
If the table contains more than 300000 entries, {project_name} will skip the index creation by default during the automatic schema migration and instead log the SQL statement on the console during migration to be applied manually after {project_name}'s startup.
See the link:{upgradingguide_link}[{upgradingguide_name}] for details on how to configure a different limit.

=== Automatic non-blocking index creation after startup
// https://github.com/keycloak/keycloak/issues/46555

When {project_name} skips creating an index during schema migration because the table exceeds the row count threshold, the index checker now automatically creates the missing index in the background after startup on databases that support non-blocking index creation.
This applies to PostgreSQL (`CREATE INDEX CONCURRENTLY`), Oracle (`CREATE INDEX ... ONLINE`), MySQL/MariaDB (online DDL by default), and Microsoft SQL Server Enterprise, Developer, and Azure SQL editions (`CREATE INDEX ... WITH (ONLINE = ON)`).

On PostgreSQL, if an invalid index exists from a previously failed `CREATE INDEX CONCURRENTLY`, {project_name} detects it, drops it, and recreates it automatically.

On databases that do not support non-blocking index creation, or when the migration strategy is set to `manual` or `validate`, {project_name} continues to log the SQL statement for manual execution without creating the index automatically.

=== Caching of persistent user sessions disabled by default
// https://github.com/keycloak/keycloak/issues/52121

Caching of persistent user sessions in the embedded Infinispan cache is now disabled by default.
Recent optimizations to the database layer, including async commits, improved indexes, and cheaper refresh-date updates, make persistent sessions without caching a viable default.
Disabling the cache reduces memory usage and network traffic between nodes, enabling smoother rolling updates.

Users may observe increased database connection usage and higher CPU usage on the database.
For users already using persistent sessions, the database's own caching layer should prevent any additional IOPS.

To re-enable caching, set `+--spi-user-sessions--infinispan--use-caches=true+`.
This option is provided as a temporary workaround.
It is now deprecated and will be removed in a future release.

See also the <<disabling-persistent-user-sessions-volatile-sessions-is-deprecated>> section below for related changes.

=== Certificate Common Name truncated to 64 characters
// https://github.com/keycloak/keycloak/issues/51778

When {project_name} generates self-signed certificates (for example, during SAML client creation), the Common Name (CN) is now truncated to 64 characters to comply with the https://datatracker.ietf.org/doc/html/rfc5280[RFC 5280] `ub-common-name` upper bound.
Previously, values longer than 64 characters, such as long client IDs, were used as-is.
With the BouncyCastle 1.85 update, this caused certificate generation to fail.

If you have tooling that inspects the CN of {project_name}-generated certificates and expects it to match a value longer than 64 characters, be aware that the CN may now be shorter.

=== Transaction isolation level changed to READ COMMITTED for MySQL and MariaDB in stateless mode
// https://github.com/keycloak/keycloak/issues/51855

When the `stateless` feature is enabled, {project_name} now sets the transaction isolation level to `READ COMMITTED` for MySQL and MariaDB.
This prevents deadlocks that occur under concurrent logins.
If binary logging is enabled with `binlog_format = STATEMENT`, this change will cause write operations to fail.
{project_name} logs an error at startup when it detects this incompatible setting.

See the link:https://www.keycloak.org/server/db#mysql-mariadb-transaction-isolation-level-in-stateless-mode[Transaction isolation level in stateless mode] section in the database configuration guide for details on `binlog_format` requirements.

Changing the default transaction isolation level for all modes is being considered for a future release.

=== Galera Cluster considerations

=== Asynchronous commit on MS SQL Server and Oracle databases
// https://github.com/keycloak/keycloak/issues/52012

The asynchronous commit optimization, previously available only on PostgreSQL, now also supports MS SQL Server and Oracle databases.
Transactions that update only ephemeral tables like persisted user sessions, client sessions, login failures, or events will use delayed/asynchronous commit, improving throughput.
Logouts will still force a synchronous commit.

On MS SQL Server, the DBA must enable delayed durability first: `ALTER DATABASE ... SET DELAYED_DURABILITY = ALLOWED`.
On Oracle, no database-level configuration is required.
On both databases, the optimization is automatically disabled when using XA datasources (`+--transaction-xa-enabled=true+`).

You can opt out of this feature by setting `+--spi-connections-jpa--quarkus--async-commit=false+`.

=== Stateless feature requires a distinct cluster name
// https://github.com/keycloak/keycloak/issues/51855

The `stateless` feature now requires `+--cache-embedded-cluster-name+` to be set explicitly to a value other than the default `ISPN`.
{project_name} refuses to start if the `stateless` feature is enabled and this option is missing or still set to `ISPN`.

Previously, the cluster name had to be configured through the low-level SPI option `+spi-cache-embedded--default--cluster-name+` (or the environment variable `+KC_SPI_CACHE_EMBEDDED__DEFAULT__CLUSTER_NAME+`).
This option is now superseded by the first-class CLI option `+--cache-embedded-cluster-name+` (environment variable `+KC_CACHE_EMBEDDED_CLUSTER_NAME+`).

If you use the `stateless` feature, add `+--cache-embedded-cluster-name=<unique-name>+` to your startup command with a name that is unique per deployment.
Two deployments sharing the same database must use different cluster names so that cross-cluster cache invalidation works correctly.

=== First-class CLI options for cluster and node name
// https://github.com/keycloak/keycloak/issues/44605

The embedded cache cluster name and node name are now configurable with the first-class CLI options `--cache-embedded-cluster-name` (environment variable `+KC_CACHE_EMBEDDED_CLUSTER_NAME+`) and `--cache-embedded-node-name` (environment variable `+KC_CACHE_EMBEDDED_NODE_NAME+`).
These replace the low-level SPI options `+spi-cache-embedded--default--cluster-name+` and `+spi-cache-embedded--default--node-name+`.
The SPI options continue to work but the new CLI options are recommended.

The node name appears in Infinispan and JGroups log messages, metrics tags, and management tools.
By default, a random name is generated on each start, which makes it difficult to correlate metrics and logs across restarts.
Setting a stable node name improves observability, especially with tools such as Grafana dashboards and log aggregation.

*{project_name} Operator*

When deploying with the {project_name} Operator, this is now set automatically to the Kubernetes Pod name.
No additional configuration is needed.

*Standalone Kubernetes deployments (without the Operator)*

Add the following environment variable to your pod spec to set the node name to the Pod name:

[source,yaml]
----
env:
  - name: KC_CACHE_EMBEDDED_NODE_NAME
    valueFrom:
      fieldRef:
        fieldPath: metadata.name
----

*Bare-metal or VM deployments*

Pass `+--cache-embedded-node-name=<name>+` with a value that uniquely identifies each node, for example the hostname.

=== Validating cluster names when using jdbc-ping discovery
// https://github.com/keycloak/keycloak/issues/52696

{project_name} nodes that use the `jdbc-ping` cluster stack periodically check whether other {project_name} deployments with a different cluster name are connecting to the same database.
If this is detected and the `stateless` feature is *not* enabled, each node logs an error and reports itself as unhealthy via the health endpoint.

The `stateless` feature provides the cross-cluster cache invalidation mechanism that makes it safe for separate {project_name} deployments to share a database.
Without it, realm and authorization data cached by one deployment is never invalidated when the other deployment makes a change, which leads to stale caches and incorrect behavior.

*Impact on blue-green deployments*

A standard blue-green upgrade keeps only one cluster active at a time: the old cluster is fully shut down before the new one starts receiving traffic.
With this strategy, both clusters never run simultaneously, so no second cluster name is ever visible in the database and this check does not trigger.

If your blue-green process involves a brief overlap period where both clusters are up concurrently — for example, to pre-warm caches — and you use *distinct* cluster names without the `stateless` feature, both deployments will log errors and report unhealthy during that window.
This is intentional: without the `stateless` feature, neither deployment invalidates the other's caches, which is unsafe when both are serving traffic at the same time.

*Recommendations*

* *Single cluster*: no action required.
The check does not trigger.

* *Blue-green with only one cluster active at a time*: no action required.
The check does not trigger because both clusters are never running simultaneously.

* *Blue-green with a concurrent overlap period and distinct cluster names, without `stateless`*: the unhealthy status during the overlap is expected and correct.
Either accept the brief unhealthy window, avoid running both clusters concurrently, or enable the `stateless` feature.

* *Multiple independent deployments sharing the same database*: enable the `stateless` feature and assign each deployment a unique cluster name via `--cache-embedded-cluster-name`.
Without `stateless`, cross-deployment cache invalidation does not work and serving traffic from multiple deployments simultaneously leads to incorrect behavior.

=== Quarkus upgraded from 3.33 to 3.40

{project_name} now runs on Quarkus 3.40 (up from 3.33 in 26.7.0).

=== Organization identity providers now support many-to-many linking

The relationship between identity providers and organizations has changed from many-to-one to many-to-many. Previously, an organization could have multiple identity providers, but each identity provider could only be linked to a single organization. A single identity provider can now be linked to multiple organizations, with independent per-association configuration for auto-membership and membership type.

During migration, the following changes are applied automatically:

* Existing identity provider-to-organization links are migrated to the new `ORG_IDENTITY_PROVIDER` join table with `AUTO_MEMBERSHIP=true` and `MEMBERSHIP_TYPE=MANAGED`, preserving the previous default behavior. New links created after the upgrade default to `MEMBERSHIP_TYPE=UNMANAGED`.

* The `ORGANIZATION_ID` column is removed from the `IDENTITY_PROVIDER` table.

* The `ORG_DOMAIN` table is extended with new columns for domain routing: `REALM_ID`, `IDP_ID` (identity provider routing), and `AUTO_REDIRECT`. Each domain is now a first-class entity with its own routing configuration.

* Three identity provider configuration entries are migrated to the new `ORG_DOMAIN` columns and then removed:
** `kc.org.domain` -- migrated to `ORG_DOMAIN.IDP_ID` (identity provider routing). If the value was `ANY`, all domains of the organization receive the identity provider routing, except those listed in the exclusion list below.
** `kc.org.broker.redirect.mode.email-matches` -- migrated to `ORG_DOMAIN.AUTO_REDIRECT`
** `kc.org.excluded.domains` -- excluded domains are migrated with `IDP_ID=NULL` (no routing)
+
The concept of domain exclusions no longer exists as a separate setting. Instead, each domain now has its own identity provider routing configuration. A domain that previously appeared in the exclusion list is migrated with no identity provider assigned (`IDP_ID=NULL`), which means users with that email domain see the standard login form instead of being redirected. To achieve the same effect going forward, edit the domain in the organization's *Domains* tab and leave the *Identity provider* field empty. Conversely, to start routing a previously excluded domain, select the desired identity provider from the dropdown.

* Several display settings previously configured on the organization's identity provider link dialog have moved to the identity provider's own Settings page at the realm level, under the *Organization settings* section:
** *Hide on login page when organization is not resolved*
** *Show on login page for unlinked members*

* Identity provider mappers that target organization groups now store the target organization ID explicitly in the mapper configuration (`orgId` field). Previously, the organization was inferred implicitly, which only worked when the identity provider was linked to a single organization. During migration, existing mappers that target organization groups are automatically backfilled with the appropriate organization ID. After upgrading, if your identity provider is now linked to multiple organizations, create separate mappers for each organization's groups.

After upgrading, verify the domain routing and per-association configuration in the admin console:

. Navigate to each organization's *Domains* tab to confirm identity provider routing and auto-redirect settings.
. Navigate to each organization's *Identity providers* tab to confirm auto-membership and membership type.
. If you use the Admin REST API to manage identity provider-organization links, update your integrations. The `organizationId` field on `IdentityProviderRepresentation` has been replaced by a list of organization links accessible through the organization identity provider endpoints.

For details on the new configuration model, see link:{adminguide_link}#++_managing_identity_provider_++[Managing identity providers] and link:{adminguide_link}#managing-organization-domains_server_administration_guide[Managing organization domains] in the {adminguide_name}.

=== Default JPA persistence unit renamed to `<default>`

{project_name}'s default JPA persistence unit is now configured through Quarkus Hibernate ORM properties instead of an internal `persistence.xml`. As a result, the default persistence unit, previously named `keycloak-default`, is now Quarkus' default (unnamed) persistence unit, reported as `<default>`.

If a custom provider archive defines multiple persistence units within a single `persistence.xml` and an entity-less unit should load `META-INF/orm.xml`, explicitly declare the standard `<mapping-file>META-INF/orm.xml</mapping-file>` element in that `<persistence-unit>` to ensure its entities are properly bound and to prevent cross-unit mapping collisions.

// ------------------------ Deprecated features ------------------------ //
== Deprecated features

The following sections provide details on deprecated features.

=== Multi-cluster v1 (`multi-site` feature) is deprecated
// https://github.com/keycloak/keycloak/issues/52772

The `multi-site` feature, used for multi-cluster v1 deployments with an external {jdgserver_name} cluster, is deprecated and will be removed in a future major release.
The `stateless` feature (multi-cluster v2) is the recommended replacement.
It stores session data in the database, eliminating the need for an external {jdgserver_name} cluster, its cross-site replication, and the associated fencing automation.

If you are using `--features=multi-site`, migrate to `--features=stateless` before upgrading to a future release.
For detailed migration instructions, see https://www.keycloak.org/high-availability/multi-cluster-v2/migrate-from-v1-to-v2[Migrating from multi-cluster v1 to v2] in the {highavailabilityguide_name}.

=== Client certificate REST API endpoints for key pair management
// https://github.com/keycloak/keycloak/issues/49239

Several REST API endpoints under `/admin/realms/\{realm}/clients/\{id}/certificates/\{attr}` that deal with server-side key pair generation or private key storage are now deprecated:

* `POST .../generate` -- Generates a key pair on the server.
Clients should generate their own key pairs locally and upload only the public certificate.
* `POST .../upload` -- Superseded by `POST .../upload-certificate`, which is functionally identical but not deprecated.
* `POST .../download` -- Downloads a keystore containing the client's private key.
Clients should manage their own private keys.
* `POST .../generate-and-download` -- Generates a key pair and returns the private key as a keystore download.
Clients should generate their own key pairs locally.

These endpoints no longer store private keys in the database.
The `generate` endpoint returns the private key in the response but only persists the public certificate.
The `generate-and-download` endpoint returns the private key in the keystore download but only persists the public certificate.

Use the `POST .../upload-certificate` endpoint to upload a public certificate or JWKS after generating your key pair locally.

=== Introspection endpoint 'jwt' extension
// https://github.com/keycloak/keycloak/issues/51026

The proprietary {project_name} extension for invoking the introspection endpoint with the HTTP header `Accept: application/jwt` instead of `Accept: application/json` is now deprecated.
If you have a lightweight access token that you want to exchange for a full access token, use link:{securing_apps_token_exchange_link}[Token Exchange] instead.

=== 'Full scope allowed' switch on clients is deprecated
// https://github.com/keycloak/keycloak/issues/52923

The *Full Scope Allowed* switch on OIDC clients is deprecated and will be removed in a future release.

When *Full Scope Allowed* is enabled (which is the default for new clients), every access token issued for that client contains _all_ roles the authenticated user holds across all clients and the realm.
This is convenient during early development, but is a security risk in production: a single compromised token grants access to every resource the user can reach.
The correct approach is to disable *Full Scope Allowed* and explicitly configure link:{adminguide_link}#_role_scope_mappings[role scope mappings] so that each client's tokens contain only the roles that client actually needs.

==== Deprecation warning in the server log

Starting with this release, {project_name} logs a `WARN`-level message at token-issuance time for every client that still has *Full Scope Allowed* enabled.
The warning is suppressed for the built-in admin clients `security-admin-console` and `admin-cli` (see below).

To silence the warning for all other clients temporarily, disable logging for the category `org.keycloak.protocol.oidc.endpoints.TokenEndpoint.full-scope-allowed`.
However, the recommended action is to keep the warning enabled and instead migrate the clients that produce it, so that your deployment is prepared for the full removal of the switch in a future release.

==== Built-in admin clients

The built-in clients `security-admin-console` and `admin-cli` currently have *Full Scope Allowed* enabled and the deprecation warning is intentionally suppressed for them.
The {project_name} team will fix these clients in an upcoming release as part of the planned migration path.

It is not strictly needed to manually disable *Full Scope Allowed* for these clients in your own environment.
Disabling it manually can break Admin Console login immediately, and may require additional manual migration steps in future {project_name} upgrades.
If you prefer to disable it for the built-in clients, you may need additional steps, for example, create a client scope with the appropriate role scopes and add that client scope to the built-in admin clients.
{project_name} will provide a migration path for both cases (environments where built-in admin clients still have *Full Scope Allowed* enabled and environments where it has already been disabled).

==== How to migrate your own clients

. For each client that triggers the deprecation warning in the log, open the client in the Admin Console, navigate to *Client scopes* → the dedicated client scope → *Scope*, and disable *Full Scope Allowed*.
. Explicitly add the role scope mappings that the client requires under the same *Scope* tab or on the linked client scopes.
. Use the *Client scopes* → *Evaluate* tool (See details link:{adminguide_link}#_client_scopes_evaluate[here]) to verify that the resulting token contains exactly the roles the client needs.

To enforce that all newly created or updated clients in a realm have *Full Scope Allowed* disabled automatically, configure a client policy with the `full-scope-disabled` executor.
See link:{adminguide_link}#_full_scope_disabled_policy[Enforcing Full Scope Allowed to be disabled] in the {adminguide_name} for step-by-step instructions, including how to exclude built-in clients from the policy.

=== Client switches in the 'OpenID Connect Compatibility Modes'
// https://github.com/keycloak/keycloak/issues/51921

Several client switches in the admin console under **OpenID Connect Compatibility Modes** were introduced for backwards compatibility with older OIDC/OAuth2 client adapters.
These switches are now deprecated and will be removed in a future version.
Some were deprecated in previous versions.
The newly deprecated switches are:

* Exclude Session State From Authentication Response
* Exclude Issuer From Authentication Response
* Use lower-case bearer type in token responses

Update your client applications if you still rely on these switches, as they will be removed in a future version.

=== Option Revalidate Client Certificate is deprecated for the X509 user authenticators
// https://github.com/keycloak/keycloak/issues/51850

As described in the breaking changes section, the option **Revalidate Client Certificate** is deprecated for the X509 user authenticators.
This option was used to revalidate the certificate chain presented by the user against the server trust store.
In the future, revalidation will always be performed and the trust store should be configured accordingly.

=== `HttpResponse#getStatus()` and `setStatus(int)` in server SPI
// https://github.com/keycloak/keycloak/issues/49374

`org.keycloak.http.HttpResponse#getStatus()` and `org.keycloak.http.HttpResponse#setStatus(int)` are now deprecated.
These methods are not useful for JAX-RS resource endpoints because the JAX-RS runtime usually determines the final HTTP status from the endpoint return value or exception.
Use JAX-RS response handling for setting and observing status codes in resource endpoints.

=== Route in `AUTH_SESSION_ID` cookie for sticky sessions
// https://github.com/keycloak/keycloak/issues/51897

Having the load balancer route appended to the `AUTH_SESSION_ID` cookie is now deprecated.

Since the optimizations in 26.6, sticky sessions no longer bring a significant benefit given the complex setup on the proxy side to get this working.
Authentication sessions are created on the node where the browser starts the session, and while a session may move to another node on a subsequent request, the overhead is low.
Most interactions such as backchannel calls and token refreshes do not use cookies and are distributed across nodes regardless.
The recommendation is to aim for an even distribution of load across {project_name} nodes instead of using sticky sessions.

The options `+spi-sticky-session-encoder--infinispan--should-attach-route+` and `+spi-sticky-session-encoder--remote--should-attach-route+` will be removed in a future release.

The setting is still enabled by default to avoid breaking existing setups.
To avoid the deprecation warning at startup, set those SPI options to `false`.

[#disabling-persistent-user-sessions-volatile-sessions-is-deprecated]
=== Disabling persistent user sessions (volatile sessions) is deprecated
// https://github.com/keycloak/keycloak/issues/52121

Disabling the `persistent-user-sessions` feature (volatile sessions) is deprecated and will be removed in a future release.
Persistent user sessions will become the only supported mode.
If you have explicitly disabled persistent user sessions with `--features-disabled=persistent-user-sessions`, remove this option before upgrading to a future release.

=== In-memory login failures (`login-failures:v1`) is deprecated
// https://github.com/keycloak/keycloak/issues/52126

The previous default of storing login failure data only in the in-memory Infinispan cache (`login-failures:v1`) is deprecated and will be removed in a future release.
Login failures are now stored in the database by default (`login-failures:v2`).
If you have explicitly enabled `login-failures:v1`, plan to remove this option before upgrading to a future release.

=== Kerberos credential delegation is deprecated
// https://github.com/keycloak/keycloak/issues/44062

Kerberos credential delegation (the `gss delegation credential` protocol mapper) is now deprecated for security reasons and will be removed in a future release.
