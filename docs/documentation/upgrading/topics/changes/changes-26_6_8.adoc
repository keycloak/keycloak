== Breaking changes

Breaking changes are identified as those that might require changes for existing users to their configurations or applications.
In minor or patch releases, {project_name} will only introduce breaking changes to fix bugs.

=== Client policy source groups condition matches the full group path

The `client-updater-source-groups` client policy condition now matches groups by their full path instead of the simple group name. A configured value without a leading slash is treated as a top level group, so a condition configured with `topGroup` matches `/topGroup` and keeps behaving as before. Top level groups configured by their simple name do not require any change.

Only the conditions configured with the simple name of a subgroup need to be updated to the full path of that group, for example `/topGroup/level2group`.

=== X.509 authenticators process key usage and extended key usage validations correctly

The X.509 user authenticators (**X509/Validate Username Form** for browser authentication and **X509/Validate Username** for direct access grants) include two optional configuration settings for key usage and extended key usage. These settings allow administrators to validate the presence of specific purposes within the corresponding certificate extensions. Previously, validation only occurred if the extension was marked as critical in the certificate. Starting with this version, validation is performed regardless of the critical status.

Although the previous behavior was considered a bug, a new provider option is available for each authenticator to revert to the legacy validation if necessary.

[source,bash]
----
bin/kc.[sh|bat] start --spi-authenticator--auth-x509-client-username-form--legacy-critical-behavior true \
  --spi-authenticator--direct-grant-auth-x509-username--legacy-critical-behavior true
----

See link:{adminguide_link}#_x509[X.509 client certificate user authentication] for more information.

== Notable changes

Notable changes may include internal behavior changes that prevent common misconfigurations, bugs that are fixed, or changes to simplify running {project_name}.
It also lists significant changes to internal APIs.

=== Conditional OTP authenticator now requires a trusted proxy for header-based rules

The `Skip OTP for Header` (`SKIP_OTP_FOR_HTTP_HEADER`) option in the Conditional OTP authenticator now verifies both that Keycloak is configured in reverse proxy mode (via `--proxy-headers`) and that the request arrived through a https://www.keycloak.org/server/reverseproxy#_trusted_proxies[trusted proxy]. If proxy headers are not configured, or if the proxy is not trusted, the skip-header rule is ignored and OTP is not skipped.

The `Force OTP for Header` (`FORCE_OTP_FOR_HTTP_HEADER`) option is not affected by this change because forcing OTP is always the safer direction.

Both options should only be used when {project_name} is configured in reverse proxy mode with headers correctly overwritten by the proxy. Without this, any client can inject a matching header value in their request and influence the OTP decision. See https://www.keycloak.org/server/reverseproxy#header-filtering-recommendations[Header filtering recommendations] for more details.

=== New executor to secure client cluster node registration

A new client policy executor, `secure-client-node-hostname`, is available to address server-side request forgery (SSRF) via the legacy adapter cluster node registration endpoint (`/clients-managements/register-node`).
Without this executor, a confidential client could register an attacker-chosen hostname that {project_name} would later use as the destination for management callbacks such as logout propagation and push-revocation.

*This protection is opt-in and is not active after upgrading unless explicitly configured.*

If your deployment uses the legacy adapter node registration feature (Wildfly/JBoss adapter or any application that calls `register-node` directly), add the `secure-client-node-hostname` executor to a client policy and configure at least one allowed hostname pattern. Node registrations that do not match any pattern are rejected.

Hostnames must be supplied as a DNS name or IP address without a port number. Port suffixes (for example, `app.example.com:8443`) are always rejected regardless of the configured patterns.

If you plan to enable this executor, audit the `registeredNodes` map for any affected clients before activating the policy. Any entry that contains a port suffix will no longer be accepted at registration time. Follow these steps in order:

. *Delete* each existing `registeredNodes` entry that would not satisfy the intended allowlist, using the admin API endpoint `DELETE /admin/realms/{realm}/clients/{id}/nodes/{node}` or via the admin console.
. *Enable* the policy with the `secure-client-node-hostname` executor added.
. *Register* each replacement hostname through `POST /admin/realms/{realm}/clients/{id}/nodes` so that the new entry is validated against the active policy.

Re-registering a replacement hostname without first deleting the old entry leaves the old key in the map, which {project_name} continues using for management callbacks regardless of the active policy.

=== Certificate Common Name truncated to 64 characters
// https://github.com/keycloak/keycloak/issues/51778

When {project_name} generates self-signed certificates (for example, during SAML client creation), the Common Name (CN) is now truncated to 64 characters to comply with the https://datatracker.ietf.org/doc/html/rfc5280[RFC 5280] `ub-common-name` upper bound.
Previously, values longer than 64 characters, such as long client IDs, were used as-is.
With the BouncyCastle 1.85 update, this caused certificate generation to fail.

If you have tooling that inspects the CN of {project_name}-generated certificates and expects it to match a value longer than 64 characters, be aware that the CN may now be shorter.

=== Kerberos username/password authenticator performs local service-ticket round trip

Previously, the Kerberos provider authenticated the user only against the KDC server by performing an AS-REQ/AS-REP exchange. Consequently, authentication could succeed against an unintended or rogue KDC if it was inadvertently selected. This applied only to direct Kerberos username and password authentication, never to browser-based SPNEGO/negotiate authentication.

Starting with this release, after authenticating the user, {project_name} performs an additional service-ticket round trip for its configured service principal. A service ticket is requested using TGS-REQ/TGS-REP and validated with the configured local keytab.

Although no issues are expected, the previous behavior can be restored with the following provider options for the LDAP and Kerberos standalone providers:

[source,bash]
----
bin/kc.[sh|bat] start --spi-storage--ldap--disable-kerberos-authentication-round-trip true \
  --spi-storage--kerberos--disable-kerberos-authentication-round-trip true
----
