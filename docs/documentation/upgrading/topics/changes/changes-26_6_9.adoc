== Breaking changes

Breaking changes are identified as those that might require changes for existing users to their configurations or applications.
In minor or patch releases, {project_name} will only introduce breaking changes to fix bugs.

=== CIBA requires client authentication (CVE-2026-109082)
// https://github.com/keycloak/keycloak/issues/53937

The Client Initiated Backchannel Authentication (CIBA) grant is now rejected for public clients, as required by the https://openid.net/specs/openid-client-initiated-backchannel-authentication-core-1_0.html#rfc.section.7.1[CIBA specification], which mandates client authentication on both the backchannel authentication endpoint and the token endpoint.
Previously, a public client with the CIBA grant enabled could complete the flow without authenticating and obtain tokens for the approving user.

=== Session note mappers no longer expose internal credentials or user models

When a user authenticates through an external identity provider, {project_name} stores the tokens issued by that provider as notes on the user session.
The supported way to retrieve them is the broker token endpoint; its authorization requirements depend on the enabled Identity Brokering API version.
Previously, the *User Session Note* mapper copied any session note into a token claim without checking what the note held.
An administrator who only held the `manage` permission on a single client could therefore configure a mapper for `FEDERATED_ACCESS_TOKEN` and receive the upstream token of every user who logged in to that client, bypassing the broker token endpoint's authorization checks entirely.
The same applied to the SAML *User Session Note* mapper, which copied the note into a SAML attribute.

Both mappers now refuse to read the session notes that hold identity provider tokens: `FEDERATED_ACCESS_TOKEN`, `FEDERATED_REFRESH_TOKEN`, `FEDERATED_TOKEN_EXPIRATION`, and `FEDERATED_ID_TOKEN`, together with the per-provider forms such as `FEDERATED_ACCESS_TOKEN:my-idp`.
They also refuse to read `keycloak.userModel`, which holds the serialized user model when the experimental transient-users feature is used.
This internal representation includes user attributes, role and group identifiers, and consent data, and must not be copied wholesale to application tokens.
The documented Kerberos GSS credential delegation mapper and ordinary application session notes remain supported.

Creating or updating a client with such a mapper is rejected with a `400 Bad Request`, and so is importing a realm that contains one.
A mapper that already exists, because it was configured before upgrading, is retained but no longer produces a claim or an attribute, and {project_name} logs a warning naming the mapper and the client.

Existing deployments continue to start because the mappers are read from the database rather than imported, but a client with such a mapper cannot be updated until the mapper is removed.
If you provision realms from an exported JSON file, remove the mapper from the file before importing it again.

After upgrading, if any of your applications read an identity provider token from a token claim or a SAML attribute, change them to call the broker token endpoint; its authorization requirements depend on the enabled Identity Brokering API version.
For more details, see the link:{adminguide_link}#retrieving-external-idp-tokens[Retrieving external IDP tokens] section of the {adminguide_name}.

=== Protocol mappers are validated when a client or a client scope is written as a whole

Previously, a protocol mapper was validated only when it was written through the mapper endpoints of the Admin REST API.
A mapper sent as part of a client or a client scope, such as during client registration, partial import, or realm import, was stored without being validated, so a mapper rejected by one path was accepted by another.

Starting with this release, every protocol mapper of a client is validated whenever the client is created or updated as a whole, using the same rules as the mapper endpoints. Client scope creation and realm import also validate their protocol mappers.
A mapper with an invalid configuration is now rejected with a `400 Bad Request`, where it was previously stored and silently ignored, or failed later at runtime.

The validation covers all the mappers of the client, not only the one being changed.
A client that carries a mapper stored before the upgrade whose configuration is no longer valid cannot be updated at all, even for an unrelated field, until that mapper is corrected or removed.
Updating an existing client scope does not revalidate its stored mappers.

Existing deployments continue to start, because mappers that are read from the database at startup are not validated.
If you provision realms from an exported JSON file, import the file once after upgrading to find out whether it contains a mapper that is now rejected.

=== Stricter enforcement of the requested level of authentication
// https://github.com/keycloak/keycloak/issues/53157

Previously, {project_name} could complete a login at a lower level of authentication than the client requested, when the authentication flow skipped the steps for the requested level, usually because the user already had a session.
{project_name} now rejects such logins.
For OpenID Connect clients, the requested level is the level of an essential `acr` claim.
For SAML clients, when the `step-up-authentication-saml` preview feature is enabled, it is the level of the requested authentication context or of the minimum ACR value of the client.
The level is now enforced in every authentication flow, including flows without a `Conditional - Level Of Authentication` condition and the registration and reset credentials flows.
An active login in a flow without the condition now always reaches at least level 1, and the `acr` claim reports it accordingly.

A rejected interactive login ends on an error page.
A rejected passive login returns the error `unmet_authentication_requirements` or `login_required` to an OpenID Connect client and the `NoAuthnContext` status to a SAML client.
For the level that each flow reaches, see link:{adminguide_link}#_step-up-flow[Creating a browser login flow with step-up mechanism] in the {adminguide_name}.
