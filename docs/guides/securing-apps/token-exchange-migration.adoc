Legacy Token Exchange version 1 (V1) was removed in {project_name} 27.
This guide describes how to migrate applications that used V1 in earlier versions to Standard Token Exchange version 2 (V2) or other supported features in {project_name} 27.
The V1 examples and configuration descriptions are historical references for applications upgrading from earlier versions.
V2 is the officially supported token exchange implementation aligned with link:https://datatracker.ietf.org/doc/html/rfc8693[RFC 8693].

[[_migration-paths]]
The migration path depends on the legacy token exchange scenario:

* **Internal-internal exchange**: Follow <<_migration-internal-internal,Migrating internal-internal Token Exchange V1 to V2>> below.
* **Internal-external exchange**: See link:{developerguide_link}#identity-brokering-apis[Identity Brokering APIs] for retrieving external provider tokens.
* **External-internal exchange**: See <@links.securingapps id="oauth-identity-authorization-chaining-across-domains" /> for using Standard Token Exchange V2 with JWT Authorization Grant.
* **Subject impersonation**: V2 does not support the `requested_subject` parameter. For a separate flow based on user consent, see the preview delegation feature in <@links.securingapps id="token-exchange" anchor="_token-exchange-delegation" />.

Delegation is not a direct replacement for `requested_subject`. It requires the `token-exchange-delegation` and `parameterized-scopes` features, FGAP V2 delegation permissions, user consent, and an `actor_token` in the exchange request. Follow the complete delegation flow in the linked documentation.

[[_migration-internal-internal]]
== Migrating internal-internal Token Exchange V1 to V2

This chapter covers exchanges where the subject token and the exchanged token are issued by the same realm.

[[_migration-overview]]
=== Migration Overview

Token Exchange V2 is a more secure and standards-compliant implementation than V1. The migration involves several key changes:

* **Requester clients must be confidential** - V2 does not support public clients sending token exchange requests
* **Scope and audience behavior differs** - How these parameters are interpreted has changed significantly
* **Authorization model changed** - V2 checks the subject token audience and supports optional client policies instead of fine-grained admin permissions
* **Request parameters changed** - V2 requires an explicit `subject_token_type` and defaults to returning an access token without a refresh token

[[_before-you-start]]
=== Before You Start

Review the application's previous V1 token exchange configuration:

. Document all clients that use token exchange
. Confirm that the clients use internal-internal exchange, where both tokens are issued by the same realm. For other scenarios, see <<_migration-paths,Migration Paths>>.
. Check if any requester clients are public
. Review your current scope and audience configuration

[[_key-differences]]
=== Key Differences Between V1 and V2

==== Confidential Client Requirement

V2 requires the requester client, which sends the token exchange request, to be confidential. This requirement does not apply to every client involved in the exchange.

[cols="2,1,1", options="header"]
|===
|Aspect |V1 (before {project_name} 27) |V2
|Public clients allowed |Yes (with limitations) |No
|Confidential clients required |No |Yes
|Client authentication required |Not always |Yes
|===

**Migration step**: If public clients previously used V1 token exchange, choose the appropriate approach:

* If a public client used V1 only to obtain fewer scopes for its own token, replace that exchange with the refresh token grant. The client can remain public.
* For V2 token exchange, convert the requester client to a confidential client.

For details on configuring a confidential client, see link:{adminguide_link}#_access-type[Client authentication] in the {adminguide_name}.

==== Scope Parameter Behavior

V2 interprets the `scope` parameter differently from V1.

**V2 behavior** (RFC 8693 - Standard Token Exchange):

For the V2 scope and audience behavior, see <@links.securingapps id="token-exchange" anchor="_standard-token-exchange-scope" />.

* `scope` parameter specifies **optional client scopes** of the **requester-client**
* When used, effective client scopes are "the default scopes together with the Optional client scopes"
* The `scope` parameter "can be used for upscoping and adding more scopes"
* Can request extra scopes and audiences not present in the subject token (unless restricted by policy)
* Requires `downscope-assertion-grant-enforcer` policy if you need strict downscoping only

**V1 behavior** (Legacy Token Exchange):

In V1, the effective client scopes were based on the target client specified by the `audience` parameter.

**Migration step**: Review all token exchange requests and update scope parameters:

**V1 behavior** (old):

- `scope` parameter specified scopes the **target client** should receive
- Scope was filtered based on the target client's configuration
- Primarily used for downscoping

**V2 behavior** (new):

- `scope` parameter specifies **optional client scopes** of the requesting client (requester-client)
- Can request optional scopes configured on the requester-client
- Can upscope (add more scopes) or downscope depending on client scope configuration

**Example migration**:

Before {project_name} 27, a V1 request exchanging to `target-client` used scopes configured on that target client:
[source,bash]
----
scope=read write
----

V2: When requesting as `requester-client`, you use optional scopes configured on requester-client
[source,bash]
----
scope=optional-scope1 optional-scope2
----

For strict downscoping only in V2, enable the `downscope-assertion-grant-enforcer` policy on the requester client. See link:{adminguide_link}#downscoping[Downscoping] in the Admin Console guide for details.

==== Audience Parameter Behavior

V2 supports the `audience` parameter with different semantics from V1. For the comparison of standard and legacy token exchange, see <@links.securingapps id="token-exchange" anchor="_standard-token-exchange-comparison" />.

[cols="1,1,1", options="header"]
|===
|Aspect |V1 (before {project_name} 27) |V2 (Standard)
|Multiple audiences |Single value only |Multiple values allowed
|Purpose |Specifies target client |Narrows down available audiences
|Token issued to |Target client specified by audience |Requesting client
|Filtering |Limited |Comprehensive (audiences and scopes)
|===

**V1 behavior** (from official comparison):

According to the official documentation:

* "Support for **single audience value**"†
* "**Token effectively issued to the client requested by the audience parameter** and using the scopes of that client"

In practice:

* `audience` parameter specified the single target client
* Access token used the target client's scope configuration and included that client as an audience, but `azp` remained the requester client
* Only a single value was supported

**V2 behavior** (from official comparison):

According to the official documentation:

* "Support for **more values as per the specification**"
* "It can be **used to narrow down the available audiences** and keep only the requested audiences"

In practice:

* `audience` parameter filters which audiences should be included in the token
* Token is issued to the requesting client (not the target client)
* Multiple values are supported: `audience=client1&audience=client2`
* Provides more fine-grained control

**Migration step**: Update your token exchange requests:

[source,bash]
.Before {project_name} 27 (V1): Single audience (target client)
----
audience=target-client
----

[source,bash]
.V2: Multiple audiences (filtered list)
----
audience=target-client1&audience=target-client2
----

In V2, the token still contains the audiences, but you can use multiple values to request multiple audiences in one exchange.

==== Authorization and Permissions

**Key change**: V2 uses a different authorization model from V1.

* **V1**: Used Fine-grained admin permissions version 1 (FGAP:v1) with per-client permission configuration
* **V2**: The subject token must contain the requester client in its `aud` claim, unless the requester is exchanging a token issued to itself. Fine-grained admin permissions are not needed. Client policies can optionally enforce additional restrictions.

NOTE: Fine-grained admin permissions version 2 (FGAP:v2) does not support token exchange permissions. There is no plan to add token exchange permissions to FGAP:v2.

**Migration action**: See <<_configuring-v2-token-exchange,Configuring V2 Token Exchange>> below for how to set up authorization for V2.

=== Update Token Exchange Requests

**Setup**:

. Convert each requester client to confidential
. Enable Standard Token Exchange switch for each requester client
. Update token exchange requests, including token types, scopes, and audiences
. Configure client policies if you need advanced authorization
. Test thoroughly

==== Request Parameters

V1 permitted omitting `subject_token_type` for a realm access token. V2 requires `subject_token_type=urn:ietf:params:oauth:token-type:access_token`. Include this parameter explicitly so that the request can be handled by V2.

V1 defaulted `requested_token_type` to `urn:ietf:params:oauth:token-type:refresh_token`, returning both an access token and a refresh token. V2 defaults to `urn:ietf:params:oauth:token-type:access_token`, returning no refresh token. If the application needs a refresh token, request it explicitly and configure the requester client as described in <<_migration-refresh-tokens,Refresh Tokens>>.

The following examples use a confidential `requester-client` to exchange a subject token for a token with `target-client` as its audience. Assume the subject token contains `requester-client` in its `aud` claim and includes the `api-read` scope. In the V1 configuration, `api-read` was configured on `target-client` and the required token exchange permission was granted. For V2, configure `api-read` as an optional scope on `requester-client`, with audience mappings that make `target-client` available.

The V1 request illustrates the application's behavior before upgrading. Use the V2 request with {project_name} 27.

[source,bash]
.Before {project_name} 27 (V1): Token types omitted, returning an access token and a refresh token
----
curl --request POST \
  'https://keycloak.example.com/realms/myrealm/protocol/openid-connect/token' \
  --user "requester-client:$CLIENT_SECRET" \
  --data-urlencode 'grant_type=urn:ietf:params:oauth:grant-type:token-exchange' \
  --data-urlencode "subject_token=$SUBJECT_TOKEN" \
  --data-urlencode 'scope=api-read' \
  --data-urlencode 'audience=target-client'
----

[source,bash]
.V2: Explicit access token types, returning an access token without a refresh token
----
curl --request POST \
  'https://keycloak.example.com/realms/myrealm/protocol/openid-connect/token' \
  --user "requester-client:$CLIENT_SECRET" \
  --data-urlencode 'grant_type=urn:ietf:params:oauth:grant-type:token-exchange' \
  --data-urlencode "subject_token=$SUBJECT_TOKEN" \
  --data-urlencode 'subject_token_type=urn:ietf:params:oauth:token-type:access_token' \
  --data-urlencode 'requested_token_type=urn:ietf:params:oauth:token-type:access_token' \
  --data-urlencode 'scope=api-read' \
  --data-urlencode 'audience=target-client'
----

For the complete V2 request and response parameters, see <@links.securingapps id="token-exchange" anchor="_standard-token-exchange-request" />.

[[_configuring-v2-token-exchange]]
=== Configuring V2 Token Exchange

==== Enable the Feature

Standard Token Exchange V2 is enabled by default. If it was disabled, enable it:

[source,bash]
----
bin/kc.[sh|bat] start --features=token-exchange-standard
----

==== Configure Requester Client

For each client that sends token exchange requests:

. Go to *Clients* and select your client.
. Open the *Settings* tab and find the *Capability config* section.
. Toggle *Client authentication* to *On* and enable *Standard Token Exchange*.
. Save the configuration.
. Configure the authentication method in the *Credentials* tab, such as *Client secret* or *Signed JWT*.

.Enabling Standard Token Exchange V2
image::token-exchange-switch.png[Enable Standard Token Exchange V2]

For the client enablement requirements, see <@links.securingapps id="token-exchange" anchor="_standard-token-exchange-enable" />.

The optional token expiration and refresh token settings are in the *Advanced* tab, under *OpenID Connect Compatibility Modes*:

* *Allow exchange token expiration after subject token expiration*: Leave this off to keep exchanged access and ID token expiration capped by the subject token expiration.
* *Allow refresh token in Standard Token Exchange*: Configure this only if the application needs a refresh token, as described below.

[[_migration-refresh-tokens]]
===== Refresh Tokens

V2 returns a refresh token only when the request includes `requested_token_type=urn:ietf:params:oauth:token-type:refresh_token` and the requester client allows it. Enabling refresh tokens on the client alone does not cause V2 to return one.

. In the *Advanced* tab, open *OpenID Connect Compatibility Modes*.
. Ensure *Use refresh tokens* is *On*.
. Set *Allow refresh token in Standard Token Exchange* to *Same session*.
. Save the configuration.

The available values are *No* (the default) and *Same session*. With *Same session*, the refresh token must use the same user session as the subject token. Subject tokens from transient or offline sessions cannot be exchanged for refresh tokens, and requesting an offline token with `scope=offline_access` is not supported.

.Configuring Refresh Tokens in Standard Token Exchange V2
image::token-exchange-switch-refresh.png[Configure refresh tokens in Standard Token Exchange V2]

WARNING: A refresh token allows the requester to obtain tokens beyond the subject token expiration, even when *Allow exchange token expiration after subject token expiration* is off. Consider whether the application needs a refresh token.

For the complete refresh token restrictions, see <@links.securingapps id="token-exchange" anchor="_standard-token-exchange-details" />.

==== Configure Client Scopes

Configure scopes on the requester client. This is a **key behavioral difference** between V1 and V2:

* **V1**: Scope parameter was based on the scopes of the "target" client specified by audience parameter (downscoping only)
* **V2** (from official docs): "The `scope` parameter in the token exchange request has the same meaning as other grants... the effective client scopes are the default scopes together with the Optional client scopes" of the **requester-client**

This means in V2, you configure scopes on the **requesting client**, not the target client.

Steps:

1. Go to *Clients* -> select your client (the requester client)
2. Click the *Client Scopes* tab
3. Configure *Default Client Scopes* and *Optional Client Scopes*:
   * **Default Client Scopes**: Used for initial scope resolution whether or not a `scope` parameter is supplied, such as `profile` and `email`. Audience filtering can subsequently remove a default client scope if it contains client role mappings but none match a requested audience.
   * **Optional Client Scopes**: Can be requested via the `scope` parameter in the token exchange request (e.g., custom-api-read, custom-api-write)
4. These configured scopes will be available for token exchange requests
5. (Optional) Use the *Client scopes evaluate* tab to test scope resolution for a specific user

For detailed information on client scopes, see link:{adminguide_link}#_client_scopes[Client Scopes] in the Admin Console guide.

==== Configure Client Policies (Optional)

According to the official documentation: "**Fine-grained admin permissions (FGAP) are not needed for the standard token exchange.**" Client policies are **optional** and only needed if you want to enforce specific authorization rules.

When to use Client Policies:

* You want to restrict what scopes can be requested via token exchange
* You want to enforce strict downscoping only (no upscoping)
* You need custom conditions based on client, scope, or roles

If you don't need these restrictions, you can skip this section entirely - V2 token exchange works without client policies.

If you do need them, configure a client profile and attach it to a policy:

. Go to *Realm Settings* -> *Client Policies*.
. In *Profiles*, create or update a client profile and add the required executors. For strict downscoping, add `downscope-assertion-grant-enforcer`. Save the profile.
. In *Policies*, create or update a policy and attach the client profile.
. Add a `grant-type` condition and select `urn:ietf:params:oauth:grant-type:token-exchange` in *Grant Types*.
. Enable the policy and save the configuration.

For detailed information, see link:{adminguide_link}#client_policies[Client Policies] in the Admin Console guide and <@links.securingapps id="token-exchange" anchor="_standard-token-exchange-details" />.

[[_step-by-step-migration]]
=== Step-by-Step Migration Checklist

Follow this checklist to migrate each client:

==== Phase 1: Assessment (Before Migration)

* [ ] Document current client configuration:
** Client ID and name
** Is it currently public or confidential?
** What token exchange flows does it use?
** Current scope configuration
** Current audience configuration
** V1 fine-grained permissions from the application's previous configuration
* [ ] Confirm that the migration covers internal-internal exchange. For other scenarios, see <<_migration-paths,Migration Paths>>.

==== Phase 2: Preparation (Pre-Production)

* [ ] Create a test realm or test client in {project_name} 27 for validation
* [ ] Enable Standard Token Exchange V2 in the test environment and on the test requester client
* [ ] Convert test client to confidential:
** Go to the *Settings* tab and find *Capability config*
** Toggle *Client authentication* to *On*
** Configure the client authentication method in the *Credentials* tab
** Store credentials securely
* [ ] Configure test client scopes:
** Add necessary optional client scopes
** Verify scope resolution in Admin Console
* [ ] Update token exchange requests:
** Remove V1-specific parameters
** Set `subject_token_type=urn:ietf:params:oauth:token-type:access_token`
** Explicitly request and enable refresh tokens if the application needs them
** Update scope parameters to use the requester client's scopes
** Update audience parameters if using filtering
* [ ] Test token exchange:
** Verify the subject token includes the requester client in `aud`, unless the requester exchanges its own token
** Verify exchanged token has expected scopes and audiences
** Verify expiration behavior

==== Phase 3: Configuration (Production)

* [ ] Configure a confidential production requester. For browser or native applications that cannot protect credentials, keep their clients public and use a separate confidential backend requester:
** Select the confidential requester in *Clients*, open *Settings*, and find *Capability config*
** Toggle *Client authentication* to *On*
** Generate and rotate client credentials in the *Credentials* tab securely
** Deploy credentials only to trusted server-side applications; never embed them in public applications
* [ ] Enable the *Standard Token Exchange* checkbox in *Settings* -> *Capability config*
* [ ] Configure client scopes in production
* [ ] Deploy client policy rules if needed
* [ ] Update all client applications:
** Update token exchange requests with new parameters
** Add error handling for new error codes
** Test with new V2 behavior
* [ ] Verify the requester uses V2 authorization checks rather than legacy token exchange permissions
* [ ] Monitor logs and metrics:
** Watch for token exchange failures
** Verify requester clients are confidential
** Confirm scopes and audiences match expectations

==== Phase 4: Validation (Post-Migration)

* [ ] Test all internal-internal token exchange scenarios:
** Basic subject token exchange
** Multiple audiences (if used)
** Scope filtering, including default scopes filtered by audience
** Refresh token requests (if enabled)
* [ ] Verify error handling:
** Invalid subject token
** Public client rejection
** Insufficient audience
** Consent validation
* [ ] Performance testing:
** Measure token exchange latency
** Compare latency with measurements taken before the upgrade, if available
* [ ] Confirm migrated applications no longer send V1-specific requests

[[_common-migration-issues]]
=== Common Migration Issues and Solutions

These issues are based on the documented differences between V1 and V2 token exchange behavior.

==== Issue 1: Public Client Rejected

**Problem**: Token exchange fails with error indicating client is public

**Cause**: According to official documentation: "It is not supported for public clients to send the token exchange requests."

**Solution**:

If the public client exchanges its own token only to obtain fewer scopes, use the refresh token grant instead. For V2 token exchange, configure a confidential requester client:

1. Convert the requester client to confidential
2. Configure client credentials in the *Credentials* tab
3. Update all systems with the new client credentials

==== Issue 2: Scope Not Working as Expected

**Problem**: Token doesn't have expected scopes after exchange

**Cause**: V2 scope behavior is requester-centric (not target-centric like V1). Official docs: "The `scope` parameter in the token exchange request has the same meaning as other grants... the effective client scopes are the default scopes together with the Optional client scopes" of the requester-client.

**Solution**:

1. Review the scope parameter - it should reference requester client's scopes (not target client's)
2. Configure optional client scopes on the requester client
3. Use Client scopes evaluate tab to test scope resolution
4. For strict downscoping, enable the  `downscope-assertion-grant-enforcer` client policy

==== Issue 3: Audience Filtering Not Working

**Problem**: Token contains different audiences than requested

**Cause**: V2 audience parameter filters available audiences, it doesn't add new ones. Official docs: "The `audience` parameter can be used to filter the audiences... However, this parameter will not add more audiences."

**Solution**:

1. Configure client scopes and audience mappings on the requester client so that the requested target audiences are available. Those target audiences do not need to be present in the subject token.
2. Verify that the subject token includes the requester client in its `aud` claim, unless the requester exchanges a token issued to itself. This is a separate authorization check.
3. Use the *Client scopes evaluate* tab to verify the resulting scopes and audiences for the user.
4. Use multiple `audience` parameters if requesting multiple audiences: `audience=client1&audience=client2`
